# Agent Note: 来源语义路由  从"无差别并发 42 个"到"按话题族选 19 个"

Status: implemented

- 影响: `components/HX-Sagasu/src/route-sources.ts`（新建）、`src/recall.ts`（层内路由 + `ctx.route` 开关）

## Problem

上一轮把来源从 26 扩到 44 后暴露：**查询「美国 GDP 增速」召回了 `uniprot`（蛋白质）
与 `rcsb_pdb`（蛋白质结构）**  完全不相关。原因是 **第 1 层 31 个来源被无差别并发查询**。

消融量化了代价（「阿司匹林 相互作用」，强制跑完所有层）：

| | 调用来源 | 耗时 | 命中 |
|---|---|---|---|
| 路由关 | **42** | **108.3s** | 21 |
| 路由前（本轮的起点） | 42 | 108s | 21 |

**108 秒、42 个请求，其中约 2/3 注定返回不相关内容或空。**

## Decision

**按"话题族"路由，而不是按"来源自述词"匹配。**

### 第一版设计被实测推翻（重要）

第一版我给每个来源写了一段"擅长什么"的描述（如 `juejin: '掘金 前端 后端 编程 教程 实战 面试 中文技术'`），
用查询词与它做**余弦相似度**，相似度为 0 就跳过。

**实测立刻暴露根本缺陷**：

```
查询 "Rust 所有权"  → 跳过 juejin
  理由: 与「掘金」的能力描述零交集（14 个能力词全未命中）
  ← 而 juejin 恰恰最该查
```

同理 `duckduckgo`（通用兜底）被**所有**查询跳过。

**错在语义层不匹配**：我用"来源的自述词"去匹配"查询的话题词"。
而 `Rust 所有权` 与 `juejin` 的关系不是"词重合"，是"**话题类别**归属" 
编程问题 → 技术社区。

> **类别是有限集，可以枚举；话题是无界的，枚举不了。**

### 所以：查询先判话题类别，来源声明它覆盖哪些类别

9 个类别：`code` / `academic` / `biomedical` / `science` / `finance` / `legal` /
`general` / `media` / `social`，外加 `'*'` = 全域来源。

**判据（只跳"话题类别零交集"）**：

| 情形 | 行为 | 理由 |
|---|---|---|
| `tier === 0` | **永不跳** | 第 0 层只有 11 个，省下的少、误跳的代价大 |
| 来源含 `'*'` | **永不跳** | 通用搜索/百科"什么都能问" |
| 查询无法归类 | **全查** | 判不出类别时跳过任何来源都是赌 |
| 来源无话题声明 | **不跳** | 宁可多查，也不因"我们没写声明"而丢证据 |
| 类别有交集 | 查 | 跨领域问题命中多个类别，任一成立即查 |
| 类别零交集 | 跳 | 唯一敢跳的情形 |

**代价不对称是这里唯一的判据**：误跳 → **证据永久丢失且用户看不见**；
误查 → 浪费一次请求，结果仍会被排序判据筛掉。

### 消融结果

| | 调用来源 | 耗时 | 命中 |
|---|---|---|---|
| 路由关 | 42 | **108.3s** | 21 |
| **路由开** | **19** | **76.4s** | 20 |

**省下 23 个请求（-55%）、耗时降 30%，命中只差 1 条。**

## Alternatives considered

- **照搬 argo 的 `domain_profiles.json`**（它的 TF-IDF 路由数据）：省掉写词表的工作。**否决理由**：实测它只覆盖 **65/157** 个引擎，而**我们接的 44 个来源里只有 12 个有文档**  照搬意味着 **32 个来源无法参与路由**，等于没做。
- **沿用第一版"逐词余弦"**：实现更"算法化"，且能给出连续的相似度分数。**否决理由**：**实测推翻了它**  「Rust 所有权」跳过 `juejin`。它匹配的是"来源怎么描述自己"，而路由需要的是"查询属于哪个话题"。**词表可以补，但补不完**（见下方残留缺口）；类别是有限集，补得完。
- **只查 top-k 个来源**（如最像的 5 个）：省得更多。**否决理由**：**太激进**。路由的产出应该是"跳过注定为空的"，不是"只信最像的几个"。一个跨领域问题可能同时需要学术源与社区源，top-k 会切掉其中一族。**当前 -55% 已经够用，再省就是拿证据换时间。**
- **把路由分用于结果排序**：让"更贴主题的来源"排前面。**否决理由**：违反第一轮就立的铁律  **各来源自报分口径不可比，不做跨来源融合**。而且路由分是"来源级"的，把它加到"条目级"的排序里会让同一来源的所有条目获得同样的加成，等于按来源分组，而那是**来源契合档**已经在做的事。
- **不做路由，靠减少来源数量控制成本**：更简单。**否决理由**：**广度是目标第 (1) 项的核心**（"覆盖公域权威平台"），砍来源是往回走。而路由让我们**同时**拥有广度与成本。
- **给"无法归类"也猜一个默认类别**（如 `general` 对应全查）：实现更统一。**否决理由**：那正好是当前行为（`general` 在全查分支里），但**显式区分"判不出"与"通用话题"**有价值  前者是判据不成立，后者是判据成立但结果是通用。当前实现让它们走同一条路（全查），语义上更诚实。

## Consequences

- **查询耗时从 108s 降到 76s**（-30%），请求数 -55%。这直接降低了 argo 上游的限流压力
  （GitHub 10 次/分已实测撞过）。
- **`ctx.route === false` 可关闭路由**  供消融与调试。这是本轮做消融的接口。
- **路由**不参与排序**：`keep` 保持 `SOURCES` 登记顺序（有测试锁住）。
- **残留缺口（诚实记录）**：**话题词表是不完备的**。实测 `阿司匹林 相互作用` 最初判不出
  `biomedical`（词表里没有具体药名），补了才通过。**任何未收录领域的新词都会掉进"无法归类"→ 全查** 
  那会退化成没有路由。这个退化是**安全方向**的（多查而非漏查），但收益消失。
  真正解法需要语义模型，不是更多正则。
- **未接**：路由分没有"来源质量"维度（argo 有 `_engine_weight`），
  也**没有配额感知**（argo 的 `_quota_ratio`） 后者是独立的下一步。
