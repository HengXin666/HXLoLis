# Agent Note: 平台适配器止于 L0，覆盖率由登记表算出而不是手写

Status: implemented

- 影响: `components/HX-Sagasu/src/adapters/{adapter,bilibili,telegram,registry}.ts`

## Problem

目标要求接入 tg、discord、X.com、小红书、小黑盒、百度贴吧、B站、YouTube 八个私域/垂直平台。此前实测结论是 **1/8 可用**但那只是"argo 里有没有能跑的引擎"，不是"我们自己能不能取到结构化数据"。两件事完全不同：argo 的引擎是它自己维护的抓取器，我们需要的却是**带楼层与引用关系的对话结构**。

同时有两个已经踩过的坑必须在架构上封死：

1. **失败被吞成空结果**。argo 的 `safe_search` 装饰器与 `_run` 把引擎异常与非零退出统一吞成空结果，"外部 CLI 没装"因此被伪装成"该查询没有内容"。如果新写的适配器沿用同样的写法，"平台挂了"会变成"这个话题没人讨论"。
2. **覆盖率被高估**。argo 注册了 4 个知乎引擎，看起来覆盖 4 份，实际共用一个密钥、实际覆盖 1 份。按"引擎数/接口数"算覆盖率是自欺。

## Decision

**适配器端口 + 响亮失败 + 登记表算覆盖率。**

1. **`ThreadAdapter` 端口**：`search` / `thread` 两个方法，返回 `RawThreadInput`。平台的全部丑陋止于这一层**适配器里不允许出现 `normalizedText`**，归一化只有一处实现（L1）。
2. **失败必须响亮**：适配器取不到数据时抛 `AdapterError`，带 `kind`（network/http/api/auth/blocked/parse/unsupported）。上层据此呈现"平台不可用/依赖缺失"，而不是一个空洞的 `[]`。
3. **能力边界写进代码**：Telegram 只读**公开频道**页，`search()` 显式抛 `unsupported` 而不是伪造一个搜索；B站 的 UA/Referer 是**必需参数**不是装饰。
4. **登记表是覆盖率的唯一事实来源**：按**平台**登记（不按引擎数），每个未接入的平台必须写明**一手实测依据**与**解锁条件**；`coverage()` 由表算出，各处不得手写数字。测试强制 `state === 'ready'` 与 `adapter !== undefined` 严格一一对应。

顺带解决了一个 L2 的真缺陷（见"实测"）。

## Alternatives considered

- **直接调用 argo 的引擎，不自己写适配器**：复用已有 168 个引擎，工作量最小。否决理由：argo 的引擎只产出 `{title,url,snippet,social_meta}`**没有楼层结构**，而"对话式语义理解"的全部价值就在楼层与引用关系上；且它的失败被吞成空结果，正是我们要防的失效模式。B站 的例子最能说明问题：argo 抓的是视频元数据，我们要的是评论区。
- **适配器里顺手做归一化**（拿到 text 就 normalize 再存）：省得下游再算一遍。否决理由：归一化一旦分散到每个适配器，就必然与 L1 的口径分叉，而分叉**不报错**只是检索悄悄失效。这与"索引与查询必须共用同一分词函数"是同一条道理。
- **失败时返回空数组并记 warning**：接口永远有返回，调用方不用写 try/catch。否决理由：这正是 argo 的现状，实测后果是"小红书依赖缺失"被当成"小红书没内容"整整一段时间，直到人工去看 stderr 才发现。空数组无法区分"真没有"与"拿不到"，而这个区分正是四态判定存在的前提。
- **把 YouTube 也在这轮实现（yt-dlp 已装 2026.08.19，1752 个 extractor）**：看起来是"顺手就能多覆盖一个平台"。否决理由：已实测的只是"yt-dlp 存在"，**评论抽取的稳定性与限流行为完全没测**。按本项目的规矩，没实测就标 `todo`，不标 `ready`把"工具在"当成"能力可用"正是此前反复踩的坑。
- **把小红书/知乎的失败直接归为"没有公开数据路径"**（`no-endpoint`）：省得给人虚假希望。否决理由：它们**有**路径（凭证/登录态），只是我们缺依赖。`no-endpoint` 与 `blocked-dep` 的区分决定了要不要去申请凭证混淆两者会让该做的事被当成做不了。

## Consequences

- 新增一个平台 = 新增一个 `ThreadAdapter` 实现 + 登记表一行，不改任何上层代码。
- 适配器未接入时 `getAdapter()` 抛错并**带上解锁条件**，调用方不会拿到 `null` 后写出空指针。
- 覆盖率会**显得更低**（2/9 而不是含糊的"支持多个平台"）这是有意的：数字必须能被一手证据支持。
- Telegram 适配器的 HTML 解析是正则，结构变化会以 `parse` 类错误响亮失败，但**需要有人来修**。
- 广播型语料的判定（楼层 ≥ 5 且参与者 ≤ 2）是**基于已观测语料**的启发式，不是通用结论；换语料应重新实测。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **64 tests / 64 pass / 0 fail**；
- 夹具取自**真实响应**（`tests/fixtures/bilibili-search.json`、`bilibili-replies.json`、`telegram-channel.json`，均于 2026-09-16 从线上采集）；
- **线上端到端实测**（非夹具）：
  - `bilibili` → 12 层 / 12 参与者 / 9 条引用链 / **0 条推断** / 首楼 2026-09-12 / 指代解析出 op
  - `telegram` → 20 层 / 首楼 2026-06-15（datetime 解析正确）
- 失败契约有测试：风控码 `-412` → `blocked`；HTTP 503 → `http`；频道不存在 → `api`；页面结构变化 → `parse`；"确实没有消息" → `[]`（唯一合法的空）。`unsupported` 不计入 `isUnavailable`"不支持"与"拿不到"是两件事。
- `stripHtml` 的截断残片处理有测试：我们对超长正文做截断，线上实测遇到过未闭合的 `<tg-emoji emoji-id="…"` 残片混进正文残片会变成"证据"。
- 广播规则有双向测试：单作者频道帖流推断数为 0；六人论坛里逐字重复仍被连上（不误伤）。
