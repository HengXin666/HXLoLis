# Agent Note: argo 会话不接受并发  闸门、分档超时、兜底裁剪

Status: implemented

Decision-ID: argo-serial-gate


## Code

- `components/HX-Sagasu/src/argo-gate.ts`

## Problem

上轮修好超时后，真因暴露出来：**argo 的 MCP server 是完全串行的。**

`mcp_transport.py:78` 的 `while True` + 单线程读 stdin  **每个请求处理完才读下一个**。

而我们的第 1 层有 **31 个来源同时发起**。实测：

| 模式 | 结果 |
|---|---|
| **串行 5 个** | 每个 500-1600ms，**全部成功** |
| **并发 31 个** | **25 秒只成功 3 个**，28 个超时 |

**这不是 argo 坏了，是我们的调用方式与它的处理模型不匹配。**

### 第二个发现：两个引擎各占满 30 秒

串行实测单个引擎耗时：

```
bilibili_hot   87ms | bilibili 248ms | baidu_baike  530ms
juejin        806ms | argo:anysearch 1028ms | hackernews 1170ms
wikipedia   12035ms | duckduckgo 30057ms | reddit 30050ms
```

`duckduckgo` 与 `reddit` **各占满 30 秒**（它们的后端实测无产出  上轮已测出 duckduckgo 两组查询均 0 条）。

**统一 60 秒的代价**：32 个来源串行最坏 `32 × 60 = 1920 秒`；实测 12 个已 90 秒。

## Decision

**三处一起改，缺一不可。**

### 一、`argo-gate.ts`  有界并发闸门，上限 **1**

我先写了上限 4（直觉上"限流到 4 能在吞吐与延迟间取折中"） **实测推翻了它**：

```
闸门=4:  31 个请求 → 成功 15 / 失败 15，耗时 133s
串行:   12 个请求 → 全部成功，      耗时  90s
```

**并发反而让它内部退化成极慢**  连本来 0.1-1.2 秒的健康引擎也开始超时。
**它不接受任何并发，所以闸门取 1。**

**`release()` 必须幂等，且必须在 `finally` 调用**  否则一次异常会永久占一个槽位，闸门逐渐堵死。

### 二、分档超时  已知慢的给 8 秒

`ARGO_SLOW_ENGINES = {duckduckgo, reddit}` 走 8 秒超时，其余 20 秒。

**依据是实测耗时与产出，不是猜测。** 保留在表里而不删  与 `ARGO_ENGINE` 的处理一致：
上游恢复后它们应当自动回到正常超时，而"删掉再没人加回来"是更坏的结果。

### 三、兜底裁剪  无法归类时不再"全查"

此前 `topics.size === 0` 时返回**全查**。理由是对的（判不出类别时跳过任何来源都是赌），
**但代价实测不可接受**：`durov telegram` → 无法归类 → 查 31 个 → **123 秒**。

**改为保留"自称通用"的（标 `'*'`）与"没声明"的，跳过"自称专精"的。**

> **这不是"赌"**  它保留的正是那些**自称通用**的来源，跳过的正是那些**自称专精**
> 而查询又没命中其专精的。**判据仍然来自来源自己的声明。**

## 我在第三处犯的错（测试抓到了）

第一版的兜底分支**漏了 `tier === 0` 检查**  它在 tier 检查**之前**就 `return` 了，
于是 `crossref`/`pubmed` 被判"只覆盖 academic/biomedical"而跳过。

**实测 6 条层级行为测试因此变红**  而那正是它们存在的意义：
"**权威层永不跳过**"是一条贯穿全部路由分支的约束，**不是主分支的局部规则**。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **把闸门做成可配置**（环境变量）：更灵活。**否决理由**：**上限由 argo 的实现决定（串行）**，不是我们的运行时偏好。做配置只会多一个"没人会去读"的隐式分支，而当 argo 改成并发处理时这个值**要跟着改**  改在代码里更容易被发现。
- **只加闸门，不改超时**：改动更小。**否决理由**：**闸门只解决并发，解决不了"两个慢引擎各占 30 秒"**  串行之后那是纯粹的串行浪费。
- **只改超时，不加闸门**：同样更小。**否决理由**：**并发时超时短的会先死**（实测并发 31 个只有 3 个活下来），缩短超时只会让更多请求失败。
- **把慢引擎从 `ARGO_ENGINE` 删掉**：省掉它们的开销。**否决理由**：与上轮同一个论证  **上游可能恢复**，删掉之后没有任何机制提醒加回来。**记录不确定性而不是消灭它。**
- **兜底分支维持"全查"，改用别的办法限流**（如只查前 N 个）：能保住"不赌"。**否决理由**：**按什么顺序取前 N 个？** 按登记顺序是任意的  那才是赌。当前做法有明确判据（**来源自己声明通不通用**）。
- **兜底时把所有来源按实测耗时排序、取最快的 N 个**：更"优化"。**否决理由**：**它们不是"通用"只是"快"**  快而不相关的结果比慢而不相关的结果更浪费（它进了结果集，还要靠判据筛掉）。而当前判据是**相关性**，不是速度。
- **不改，只把 `--min-hits` 默认调低**：绕开触发条件。**否决理由**：上轮已经否决过同一思路  **那是把 bug 藏起来**，"下降层"是正常行为。

## Consequences

- **端到端从 123 秒（且 `exit=13` 挂死）降到 21 秒（`exit=0`）**。
- **第 1 层实际查询数**：`durov telegram` 从 31 → **8**；`Rust 所有权` 25；`阿司匹林` 22。
- **闸门是会话级的**（模块级单例） 因为会话是共享的，闸门也必须是。
- **未做**：把"哪层跑多少个"做成可观测指标（当前只能从耗时推断）。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **275 tests / 275 pass / 0 fail**（净增 3 条）
- **端到端实测**：
  ```
  修复前: 123 秒，exit=13，stdout 0 字节（挂死）
  修复后:  21 秒，exit=0，第 0 层 18 条 + 第 1 层 3 条 = 命中 21 条
  ```
- **闸门单测**：12 任务 × 100ms、上限 4 → 305ms、最大并发 4（闸门本身正确）
- **并发对照**：经 `argoFetchers` 并发 31 个 → 串行后成功 27 / 失败 3（失败的全是已知慢引擎）
- **路由裁剪实测**：`durov telegram` 31→8、`Rust 所有权` 14（第 1 层）
- **新增测试**：兜底只保留通用来源、**兜底分支里权威层仍永不跳过**（我漏过的那条）
