# Agent Note: argo 接线的三条硬约束  不接受缓存、不接受改道、缺失实现必须响亮

Status: implemented

Decision-ID: argo-wiring-three-constraints


## Code

- `components/HX-Sagasu/src/recall.ts`

## Problem

上一轮用探针发现 argo 的 **L2 缓存键不含 engine**：同一查询先用 `engine=zhihu` 查过，再用 `engine=juejin` 查**同一查询**，会拿回知乎的缓存结果。当时那条约束只写在 note 里，**没有落到代码**。

这一轮去落实它，顺带发现两个同族的问题：

**① 第 1、2 层登记了却没有实现。** `SOURCES` 有 4 个第 1/2 层来源（juejin / bilibili / telegram-public / argo:anysearch），而 `authoritativeFetchers()` **只覆盖第 0 层**。取数层对缺失实现的处理是：

```ts
const fetch = fetchers[source.id]
if (fetch === undefined) return []      // ← 静默变成"没有内容"
```

更糟的是 `usable` 过滤在**进入循环前**就把它们剔除了，于是第 1 层显示 `ran: false, skippedReason: '该层没有已登记且可用的来源'`  看起来像"这两层本来就是空的"，**实际是忘了接线**。

而"把实现缺失伪装成没有内容"正是本组件第一轮就明确否决的形态（argo 的 `safe_search` 就是那么做的）。**这个错误在我们自己的代码里活到了第 12 轮。**

**② 缓存拒绝需要一个诚实的代价评估。** 严格拒绝 cached 意味着"同一查询第二次调用会失败"。这是否会让系统不可用，必须实测而不是假设。

## Decision

**新增 `src/argo-source.ts`，把 argo 接进第 1、2 层，并施加三条硬约束。**

| 约束 | 行为 | 理由 |
|---|---|---|
| **不接受 cached** | `cached: true` → 抛 `AdapterError('argo','unsupported')` | 缓存键不含 engine，缓存里的内容不是本次请求的引擎产出的 |
| **不接受改道** | `engines_used` 与请求的 `engine` 不符（且不是 `auto`）→ 抛错 | 要求"查掘金"，不许把别处的证据当作掘金的 |
| **失败必须响亮** | 起进程失败/协议超时/工具报错 → 抛 `AdapterError` | 空数组只表示"真的查了、真的没有" |

同时修掉两个与"静默伪装"同族的缺陷：

- 取数层里 `if (fetch === undefined) return []` → 改为报 `kind: 'unwired'` 的失败项
- `usable.length === 0` 的两种含义分开：**该层没有登记来源**（正常）vs **登记了但没有实现**（未接线）。后者带 failures 上报，`ran: false`  **没有接线不是"跑过"**，这一层没发出任何请求，不构成供给

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **只把约束写进注释，不落到代码**（上一轮的做法）：最省事，而且 note 里确实写清楚了。否决理由：**注释不会拒绝缓存**。这一轮实测里 `bilibili` 请求直接返回了 `juejin` 的缓存内容如果代码不拦，这份"掘金的内容"会以"B站的结果"进入证据链并进入账本。约束写进注释与写进代码的差别，就是这份错误证据会不会被沉淀。
- **宽松处理 cached：接受它但把 `engines_used` 标进 snippet**：能让系统更"可用"，不会平白失败。否决理由：结果会带着错误的来源标签进入 `SOURCES` 的分层语义（第 1 层的"B站"与"掘金"权威性依据不同），而 `source-diversity` 等判据都按 `sourceId` 统计。**让调用方自己从 snippet 里读来源，等于把判定责任推给下游。**
- **自动重试以绕开缓存**（换个查询词再试一次）：能让失败率接近 0。否决理由：**这会让系统对用户撒谎**它悄悄改写了用户的问题去换一个缓存未命中的结果，而返回的内容也不再对应原始查询。用户问的与系统查的不再是同一件事。
- **彻底禁用 argo 缓存**：从根上解决。否决理由：那是 argo 上游的配置（且缓存对频繁重复的查询确实是合理的优化），本组件无权也无意替上游改行为。**"不接受别人的缓存策略"与"禁止别人使用缓存"是两件事。**
- **给第 1、2 层来源写原生适配器**（像 B站/Telegram 那样直连平台 API）：直接、可控、不依赖 argo。否决理由：那正是 `adapters/registry.ts` 里已经登记的事9 个平台里 7 个 blocked（缺凭证/反爬/无接口）。**argo 的价值恰恰在于它已经趟过了一部分**（实测它的 juejin 能出结果而我们没有掘金适配器）。两条路并存是对的：能直连的直连（B站/Telegram），剩下的走 argo。
- **把 `unwired` 当成"该层跳过"不报失败**：能让层级审计更干净（不会有一长串失败）。否决理由：那正是本轮要修的病。**一个 12 轮没被发现的"忘了接线"，代价是第 1、2 层从未真正工作过。**

## Consequences

- **第 1 层第一次真正有产出**：实测「Rust 所有权」→ 掘金《Rust所有权机制：内存安全和并发安全的基石！》；「CSS 作用域」→ 掘金《CSS前瞻：用 @scope 定义你的CSS作用域》。
- **严格拒绝缓存的代价经实测很小**：用 9 个唯一查询连续调用 `juejin`，**9/9 成功、0 次缓存拒绝**。缓存拒绝只发生在"同一查询被重复调用"时而那正是我们**想要**失败的时刻（否则第二个引擎会拿到第一个引擎的内容）。
- 层审计面多了 `kind: 'unwired'` 这一类失败。它让"忘了接线"在第一次运行就可见，而不是显示为"这一层本来就是空的"。
- `argo-source.ts` 依赖 `node:child_process` 的 `spawn`，但**通过 `SpawnLike` 端口注入**，所以测试是离线、毫秒级的（9 个新测试不启动任何进程）。
- **新增一条未解决的风险**：`argoFetchers` 共享一个 MCP 会话，若 argo 进程中途崩溃，剩余的来源会同时失败。当前实现把这种情况报为 `network` 失败**但它不会自动重启会话**。这与"一个来源坏了不该拖垮整层"的原则有张力，是下一步待办。
- `telegram-public` 仍未接线（它有直连适配器，但那是 `adapters/` 的路径，尚未接到 `recall` 的取数层）。**登记与实现的不一致还有一处，本轮只把它变成了可见，没有消灭。**
