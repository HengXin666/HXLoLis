## Problem

用户指出："**你应该学习 argo**"。此前我一直把它当"一个搜索源"在用（通过 MCP），**没有读过它的源码**。
本轮把它读了一遍，发现它解过的问题里有几个我们正在重犯。

## Decision

### 一、把"有没有内容"升级成"有什么内容"（`evidenceBlocksOf`）

我们原有的 `substanceOfHit` 只数**词数**（去掉查询词后还剩几个词）。它挡得住"只有标题字面重合"，
但挡不住另一类更常见的东西：**一段很长、很有文采、但没有任何可核对事实的文字。**

argo 的 `content_signals.score_evidence_density` 用证据块类型加权：
数字 +0.22 / 定义 +0.18 / 对比 +0.16 / 步骤 +0.12 / 披露 +0.08。

**这是第 18 轮那个错误的同族**：那轮是"覆盖数被丢弃，只用了布尔投影"，
这轮是"证据块类型被丢弃"只知道"有内容"，不知道"有什么内容"。

接入层内排序作**第三维分档**（前两维：覆盖数、来源契合）。仍是稳定分档，不是全序 
第 18 轮的教训：全序排序会打乱同分顺序，破坏"层内保持来源顺序"这条铁律。

### 二、限流不是故障（`getText` 的 403/429）

实测：GitHub 未认证配额 **10 次/分**，连续检索几轮就打满。此前它和"服务器坏了"一样报 `http`，
但这两件事对用户的意义**完全不同**：服务器坏了要等修复或换源；**配额用完了再等一会儿就好，而且是我自己用完的**。

argo 的做法更彻底  用 `_quota_ratio` 在**路由阶段**就降低即将耗尽的引擎权重（`tfidf_router.py:272`），
**根本不发那个注定失败的请求**。我们还没有配额账本（列为后续工作），但**至少要把话说清楚**。

保留 `code: 'http'` 不变（下游 switch 依赖它），在 message 里加可辨识前缀。

### 三、给界面加证据块标签

界面现在显示每条命中的"证据块: 数字 / 定义 / 对比"与密度值。
**理由同第 18 轮**：能被看见本身就是验证手段。只显示"有/没有内容"看不出质量差异。

## Alternatives considered

- **照搬 argo 对纯 Q&A 格式的 −0.08 扣分**：argo 有它的 GEO 语料实测支撑。否决理由：**我们没有那个实测**。照搬一个没有本机证据支持的扣分，正是本项目反复否决的形态。改为**只如实统计 `isQaFormat`、不扣分**，把判断留给调用方。测试显式锁住"两段内容逐字相同时，加不加 Q/A 标记密度必须相等"。
- **把 argo 的 `credibility = 0.40S + 0.35A + 0.15F + 0.10O` 整体搬过来**：它工程上很完整。否决理由：**最后一项 `original × 0.10` 是引擎自报分，跨来源不可比**，这是我们第一轮就立的铁律。但**要区分**：`selection`/`absorption` 是 argo 自己算的、跨来源可比的**特征**（该学），`original` 是引擎自报**分数**（该拒）。本轮只取了 `absorption` 那一维。
- **照搬 argo 的域名白名单权威分**（`AUTHORITY_TIERS` 字典）：一张表就能给每个来源打分，实现最简单。否决理由：**它是手工维护的，且会随域名变更失效**。我们选的是"机构责任 + 持久标识符"（DOI/PMID/owner）**可验证、不需维护、不随域名变更失效**。本轮读它的表反而**印证**了这个选择：表里有 `gov.cn: 1.0` 这种粒度，而 `wenshu.court.gov.cn` 必须靠单独的 JSON 覆盖修正到 0.96  **分层表在真实域名面前一定是不够用的**。
- **学 argo 用 TF-IDF 在路由阶段选来源**（`tfidf_router`，与我们的 bigram 双流同源）：能直接省掉注定返回 0 的请求（实测第 0 层 11 个源里 4 个注定为空）。**本轮没做，列为下一步**。理由：它需要给每个来源建"领域文档"语料，是一件独立的事，不该和第 18 轮的排序修复混在一次改动里。
- **不加测试，只改代码**：省时间。否决理由：**本轮新增的每个行为都至少有一个测试是"反过来问"的**  比如"真故障（500）不许被说成限流"、"没有查询词可覆盖时不受密度分档影响（不引入新的丢弃）"。正向测试证明功能存在，**反向测试证明它没有越界**。

## Consequences

- **层内排序现在是三维**：相关性档（≥1 词）→ 来源契合档 → 证据块密度档（≥0.5 即"至少两个证据块"）。**每一维都是稳定分档**，同档内保持原序。
- **密度门槛 0.5 的含义**：基线 0.15 + 长度 0.05 = 0.20 是"什么都没有"；命中任一实质特征（数字 0.37 / 定义 0.33 / 对比 0.31 / 步骤 0.27）都够不到 0.5  **所以 0.5 = "至少两个证据块"**。
- 界面显示每条命中的证据块类型与密度，浮点已取两位小数（原始值会出现 `0.6000000000000001`）。
- 限流在报错里可辨识，但**仍会消耗一次请求**（我们还没有配额账本） 这是已知的未完成部分。

- **密度维的真实局限（实测，必须记住）**：基准题 `GPT 文生图 提示词` 的最终排序是
  4 个 `gpt-image-2` 仓库（密度全 **0.2**）在前，wikipedia「ChatGPT」（密度 **0.6**）在第 5 位。
  **即：正确答案的证据块密度最低。** GitHub 仓库描述是**纯叙述句**
  （"一个支持 nano-banana、gpt-image-2 和千问的文生图模型的提示词结构化与优化工具集"）
  没有一个数字、定义、对比或步骤。

  这不是缺陷，而是**密度维只该在覆盖数分档内部生效**的证据：它没有跨档把高密度低覆盖的条目提上来。
  但它确实说明 **"密度高"不等于"是答案"**  一段维基百科介绍有数字有定义（0.6），
  却不如一句说清楚"这个工具支持 gpt-image-2 提示词优化"的仓库描述有用。

  **含义**：密度维的价值在**同档内**区分"含可核对事实的长文"与"只有形容词的长文"，
  它**不是**一个独立的答案质量判据。如果将来有人想把它提升成跨档的主排序键（这是很自然的下一步想法），
  **本基准题会立刻退化**  4 个正确答案会被维基百科和 crossref 论文压下去。

## 一次被修正的结论

**我此前（第 11 轮起）一直记着"argo 的 L2 缓存键不含 engine"这是错的。**

`cache.py:607-616` 的键是 `{kind}|{nq}|{engine}|{domain}|{mode}|{depth}`，**engine 是第三个字段**。

真因在 `cache.py:708-731`：**精确 miss 后会走语义软命中**，而 `find_similar`（`:449-490`）收了 `engine` 参数，
**函数体里一次都没引用它**（实测：函数体内 `engine` 出现次数为 0）。候选项只按 `domain = ?` 过滤。

逐条实测（2026-09-18）：

| 步骤 | 请求 | 结果 |
|---|---|---|
| 1 | `zhihu` + 查询 A | `cached:false` `used:["zhihu"]` |
| 2 | `juejin` + **同一**查询 A | `cached:true` `used:["zhihu"]` ⚠️ |
| 3 | `juejin` + **近似**查询 B | `cached:true` `used:["zhihu"]` ⚠️ |

**为什么这个修正重要**：若真信"键缺 engine"，修法是往键里加字段  而字段**本来就在**，
改完症状不变，还会让人以为已修好。**一次被污染的测量会产出一个听起来很具体、且有"实测数据"支撑的错误结论。**

**修正来源**：派子代理精读 `cache.py`（37.8KB，我此前只看过它的对外行为）。
**代码的答案一直在那里，我没有读它。**
