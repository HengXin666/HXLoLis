# Agent Note: 闸门惊群、注释与代码不符  以及一个仍未定位的 initialize 超时

Status: implemented

- 影响: `components/HX-Sagasu/src/argo-gate.ts`（`while` 重检 + 只在有空位时唤醒）、`src/argo-source.ts`（补齐上轮漏掉的 `.catch()`）

## Problem

上轮结论是"需要换工具"。本轮**换了**：不再读代码猜差异，而是**给闸门加放行时刻日志**、
**绕过全部封装直连 JSON-RPC**、**逐块替换受控复现**。

## Decision

### 一、闸门写了 `while` 重检（防惊群）

原实现是 `if (running >= limit) await once`。改为：
```js
while (running >= limit) { await new Promise(r => queue.push(r)) }
…
if (running < limit) { const n = queue.shift(); if (n) n() }   // 只在有空位时唤醒
```

**这是正确的写法**，但**它不是本次问题的根因**  实测 `running` 计数始终是 1。

### 二、补齐上轮**漏写的代码**（本轮最重要的发现）

上轮我在 `ready()` 上写了一段注释说"**不缓存失败**：置回 null，让下一次有机会重试"
**而我只写了注释，没写代码。** `readyPromise` 仍然永久缓存 rejected 值。

后果（本轮通过**闸门放行时刻日志**实测）：
```
+10624ms running=1       ← 第 1 个（真的跑了，成功）
+25635ms running=1       ← 第 2 个
+25635ms running=1 × 9   ← 其余 9 个**同一毫秒**（立即拿到缓存的 rejection）
```

**9 个来源在同一毫秒落定**，正是"同一个死 Promise 被 9 次 await"的表现。

**修法**：把注释与代码放在一起，补上 `.catch()`。

> **"注释写了而代码没写"是一个特别坏的失误类型**  它让下一个人（包括我自己）
> 以为问题已修，从而**不再去查它**。本轮我就是被它误导了一轮。

## 仍未定位的（换了工具仍没闭合）

补齐 `.catch()` 后，`literal.mjs` 从 **25s / 10 失败** 变成 **175s / 10 失败** 
**每次握手都真的等满 15 秒超时**，而**数量没变**。

**所以 `initialize` 在 `literal.mjs` / CLI 路径下真的超时，而在受控脚本里不会。**

| 路径 | 失败模式 | 结果 |
|---|---|---|
| `literal.mjs` | `id=1` initialize 超时（**全部同一个 id**） | 25s / 10 失败 |
| **CLI** | `id=8`/`id=9` initialize 超时（**id 分散**） | 25.8s / 12 失败 |
| `fullmsg.mjs`（受控，`await import`） | `argo_search` 8000ms 超时（**分档超时生效**） | 61s / **4 失败** |

**注意 CLI 与 `literal.mjs` 也不是同一个问题**  CLI 的 id 分散说明它**真的重试了 8-9 次**，
而 `literal.mjs` 全是 1 说明它**每次都拿到同一个缓存的 rejection**。

### 本轮新排除的方向（累计 17 个）

| # | 方向 | 实测 |
|---|---|---|
| 15 | **闸门惊群** | `running` 计数始终为 1（修了 `while` 但仍失败） |
| 16 | **`initialize` 在空闲后失效** | 建会话 → 等 12 秒 → 调用**成功** |
| 17 | **CLI 模块加载本身拖慢握手** | 手工复制 CLI 的 `buildFetchers` 但不跑 recall → 握手 **458ms** 正常 |

### 一个仍未验证的差异

`literal.mjs` 用**顶层 `import`**，而 `fullmsg.mjs` 用 **`await import()`** 
**这是两者唯一剩下的结构差异**。而它不该有语义影响。

## Alternatives considered

- **继续追那个差异**：更彻底。**否决理由**：本轮 14 轮 + 上轮 13 轮 = **27 轮**。而**每一条新排除都指向"代码没问题"**。**该做的是把已确认的部分固化，并把这个未闭合的现象连同 17 条排除记录留档**  下一个人不必重走。
- **把 CLI 也改成 `await import()`**（与受控版一致）：可能绕过症状。**否决理由**：**那是让代码去迁就一个未理解的故障**。如果 `await import` 真的改变了行为，那说明的是我们**对模块初始化时序的理解有缺口**  而那需要被理解，不是被绕过。
- **把 `ready` 的失败改成"抛出让整次召回终止"**：至少不会产生 10 个模糊失败。**否决理由**：**那会让"某个来源失败"升级成"整次检索失败"**  而第 0 层是好的、结果可用（24 条命中）。
- **不修那个漏掉的 `.catch()`**（反正没解决根因）：**否决理由**：它修的是**一个独立的真实缺陷**  "一次握手超时会永久毒化会话"。即使根因未定位，这个修复本身有价值。
- **不再记录**：**否决理由**：本轮**确定修了两处**（漏写的 `.catch()`、闸门惊群），且**新排除 3 个方向**。这些都必须留档。

## Consequences

- **上轮"注释写了代码没写"被修正**  这是一个**跨轮次的完整性缺口**，值得警惕。
- **闸门改为正确的 `while` 重检**（当前 `limit=1` 下行为不变，但 `limit>1` 时是必要的）。
- **CLI 的实际表现**：`exit=0`、25.8s、第 0 层完整 18 条、总命中 24 条  **可用**。
- **`initialize` 超时的根因仍未定位**，且**已确认 CLI 与 `literal.mjs` 是两种不同的失败模式**。
