# Agent Note: 一个精确复现但未根治的并发失败  以及两处已修的真 bug

Status: implemented

- 影响: `components/HX-Sagasu/src/fetchers.ts`（整层补齐避让已登记来源）、`src/argo-source.ts`（握手改懒发）
- **未解决**: 第 1 层的 argo 来源在特定调用形态下大面积超时（见下）

## Problem

### 一、第 0 层的 `wikipedia`/`hackernews` 被 argo 实现覆盖

`planFetchers` 的"argo 整层补齐"（`fetchers.ts:322`）只避让 `claimed`，
而 `claimed` **只记录 `SOURCE_PLAN` 的 primary**。

`wikipedia`/`hackernews` 的 argo 那条登记为 **fallback**（它们的 primary 是
authoritative 的原生 HTTP），于是**它们不在 `claimed` 里 → 被整层补齐覆盖成 argo 实现**。

**实测证据**：修复前报 `[argo/network]`，修复后报 `[web/network]`。

**修法**：判据从"已认领"改为"**在 `SOURCE_PLAN` 里出现过**"。

### 二、握手计时器的起点错

`ready` 在**会话创建时**就发出并挂 15 秒计时器，而第 0 层可能先跑 10 秒 
等第 1 层要用 argo 时计时器已流逝大半。**修法**：握手**懒发**。

## Decision

### 一、整层补齐必须避让**所有已登记的来源**

判据从"已认领"（claimed）改为"**在 `SOURCE_PLAN` 里出现过**" 
无论 primary 还是 fallback，它的实现都必须由 `SOURCE_PLAN` 决定。

### 二、握手改为**懒发**

计时器与"谁在用"同步起算，而不是从会话创建起算。

### 三、未定位的部分**如实记录并给出下一步**

不再继续用排除法（已 13 轮），改为**先加可观测性**（每来源进入/落定时间线），
它是可复用资产，对下一个问题同样有用。

### 未解决的部分（精确记录）

**同一个 argo 会话，不同的调用形态，失败数差 2.5 倍。**

| 路径 | 耗时 | tier1 失败数 |
|---|---|---|
| `sagasu search --min-hits 40`（CLI） | 25.5s | **10** |
| 逐字复制 CLI 逻辑的脚本（`literal.mjs`） | 25.5s | **10** |
| 早先的脚本（`faildist.mjs`，同样模块） | **72.7s** | **4** |

**失败全部是 `method=initialize` 超时 15000ms**  即**连握手都没过**。

### 已排除的方向（每一条都有实测）

1. **多会话**  `ps` 确认两边都只有 1 个 `mcp_server.py` 进程
2. **空闲导致会话失效**  空闲 12 秒后调用正常（289ms）
3. **闸门未生效**  经 `argoFetchers` 并发 11 个 → **成功 10/11**，闸门正常
4. **懒发握手**  改后仍失败
5. **第 0 层 `wikipedia` 干扰**  修掉后仍失败
6. **`adapter` 模块 / `scope-probes` 副作用导入**  二分对照：去掉任一个失败数几乎不变（10 → 9）
7. **探针残留**  发现并清理了一处 `chr(10)` 残留（**那是我自己引入的，会让 CLI 直接崩溃**），清理后仍失败

### 已确认的机制

**直接并发（绕过闸门）6 个请求 → 只成功 2 个。**
**串行 15 个来源纯网络耗时 15.2 秒**（平均 1 秒/个）。

**所以 argo 的 MCP 确实不接受并发**，而"快路径"（25.5s）与"慢路径"（72.7s）的差别
**只在于给 argo 的喘息时间**  这指向一个**时序敏感**的问题，而我**没有定位到具体的时序条件**。

### 影响与现状

- **第 0 层完整**（18 条），`exit=0`，结果可用
- **第 1 层的 argo 来源大面积失败**  那是**真实的能力损失**（有产出的来源没被用上）
- **不影响第 0 层与原生 HTTP 来源**

### 下一步的方向（明确）

1. **给 `recall` 加"每个来源的进入/落定时间戳"日志**（本轮已用 `observer` 手工做过一次，
   证明了它有效  但需要**固化成 CLI 可开关的能力**，而不是每次写临时脚本）
2. **用那个日志对比两条路径的时间线**  靠"排除法"猜差异代价太高（本轮花了 13 轮），
   **时间线是一次性能看到差异的东西**
3. **备选方案**：让 `argoFetchers` 对失败的来源**自动重试一次**（串行的重试成本可接受），
   绕过这个未定位的时序问题  但**那是绕开而不是解决**

## Alternatives considered

- **继续用排除法查**：更彻底。**否决理由**：**已花 13 轮，每轮排除的都是错误方向**。继续猜的期望收益在下降，而**加可观测性（时间线）是可复用的资产**  它对下一个问题同样有用。
- **把握手超时从 15 秒调大**：能"解决"症状。**否决理由**：**症状会以别的方式回来**（真正的机制未定位），且会让"argo 不可用"变成"要等一分钟才发现"。
- **把 11 个失败来源从 `ARGO_ENGINE` 删掉**：输出会变"干净"。**否决理由**：**那是用删掉问题来伪装解决**。实测它们**能用**（`faildist.mjs` 路径下只失败 4 个），当前失败是**调用层的问题**。
- **给失败的来源自动重试**：能绕过症状。**否决理由**：**那是绕开而不是解决**，且成功后的重试会**隐藏**"第一次为什么失败"。列为备选而非首选。
- **不记录这个未解决的问题**：省事。**否决理由**：**"同样代码不同结果"必须被记录**  它可能指向更深的非确定性，而**不记录就会在更贵的场合爆发**。本轮把它连同**已排除的 7 个方向**一起记下，是为了**下一个人不必重走**。

## Consequences

- **两处 bug 已修且验证**（wikipedia 回原生、握手懒发）。
- **第 1 层 argo 来源大面积失败未解决**  这是当前**最大的已知能力损失**。
- **我自己引入并清理了一处残留**：多轮前注入的调试探针用了 Python 的 `chr(10)`，
  留在 `scripts/sagasu.ts` 里**会让 CLI 直接崩溃**。这提醒：**临时探针必须当场清理**。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **275 tests / 275 pass / 0 fail**
- **wikipedia 修复**：`[argo/network]` → `[web/network]`
- **闸门有效性**：经 `argoFetchers` 并发 11 个 → 成功 10/11
- **并发对照**：绕过闸门并发 6 个 → 成功 2/6
- **串行耗时**：15 个来源纯网络 15.2 秒
- **复现条件**：`literal.mjs`（25.5s → 10 失败）vs `faildist.mjs`（72.7s → 4 失败）
