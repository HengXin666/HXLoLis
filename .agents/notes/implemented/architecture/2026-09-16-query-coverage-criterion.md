# Agent Note: 覆盖度  命中对查询词的覆盖率决定"这一层是否在回答问题"

Status: implemented

Decision-ID: query-coverage-criterion


## Code

- `components/HX-Sagasu/src/recall.ts`

## Problem

上一轮修好了层内排序（相关结果不再被学科语料库埋掉）。这一轮我去量"层级还会不会在错误的地方停住"，结果测出一个**比排序更根本**的失效。

九个查询、连续跑，**8/8 全部停在第 0 层**，包括：

| 查询 | 第 0 层最佳命中 | 覆盖查询词 |
|---|---|---|
| `Rust 所有权` | `@codemirror/lang-rust` | 1/2 |
| `某国内小众框架的配置怎么写` | 《框架的主要特性》 | 1/5 |
| `2026 年某某事件进展` | 《色觉研究的某些重要进展》 | 1/4 |
| `DeepSeek 最新模型发布` | 《大语言模型赋能政务智慧化服务》 | 1/4 |

后两条**原理上不可能**由学术语料库回答一个是不存在的时事，一个是产品发布。它们却各自拿到 14–15 条，并通过了**全部**判据。

与此同时，第 1 层（中文技术社区）里躺着直接答案：掘金对「Rust 所有权」返回的首条就是《Rust 所有权与借用：从堆栈开始建立心智模型》。**它从未被触达。**

根因：第 0 层是**学科语料库**，不是检索器。你给它任何字符串，它都能在自己那个子集里找到"含某个词"的东西。而既有判据全都问不到点子上`evidence-substance` 只检查"查询之外还有没有内容"，不检查"查询覆盖了多少"。

## Decision

**新增第六条充分性判据 `query-coverage`：至少有一条命中要同时覆盖 ≥ 2 个查询词、且 ≥ 50% 的查询词。**

- 取**最佳单条**而不是所有命中的并集并集会被"十条各匹配一个词"满足，那正是要防的形态
- 查询本身只有 1 个词时豁免"≥ 2"要求
- 比较**大小写不敏感**（线上标题是 `Rust`，分词器给的是 `rust`，大小写敏感会把真实命中判成未覆盖）
- 同时读 `title` 与 `snippet`

## Alternatives considered

- **什么都不做，接受"停在第 0 层"**：第 0 层的结果确实是权威的、可引用的，用户能自己判断。否决理由：**层级顺序就是优先级**，停在第 0 层等于宣称"权威层已经答上了"，而实测里它对 8/8 的查询都这么宣称包括它原理上答不了的。这个宣称是假的，而项目的铁律是"不许把失败伪装成正常"。
- **把第 0 层的 `minHits` 调高**：最省事。否决理由：实测第 0 层对**任意**字符串都返回 13–27 条，调高阈值只会让它更多地停在 L0，方向反了。条数根本不是问题所在。
- **按意图直接跳过第 0 层**（如"时事"类查询不走学术库）：听起来更根本。否决理由：这需要一张"意图 → 该走哪些层"的映射表，而实测证明意图分类本身就有误差（"什么是 HTTP 缓存"被判成 `general`）；错一次就整层跳过，代价过大。覆盖率是**从结果本身**算出来的证据，不依赖任何预判。
- **要求"覆盖查询里所有的词"**：更严，能挡掉更多空壳。否决理由：实测「Rust 借用检查器怎么用」的最佳命中覆盖 2/4"怎么""用"是虚词，要求 100% 会把真实答案也挡掉。50% + 至少两个词是能同时保住真实命中与挡掉空壳的位置。
- **用 `normalize()` 的混淆对做覆盖度匹配（让错别字也能匹配上）**：主意不错，本组件已有 `CONFUSIONS` 表。否决理由：那一层是为**检索**设计的（扩大召回），用在这里会把"匹配上"的标准放宽，而这条判据的目的恰恰是收紧。等有真实错别字用例再谈。
- **只读 `title`，不读 `snippet`**：能挡掉下面那条已知边界的失效。否决理由：`snippet` 是很多来源唯一的正文线索（Crossref 只有作者名、PubMed 只有 ID），不读它会让判据对"标题短但摘要相关"的结果误判。**这个选择带来一个我实测踩到的边界，如实记在下面。**

## Consequences

- **触达分布从「8/8 停 L0」变成「6 停 L0 / 3 停 L1」**第 1 层第一次被真正触达。
- **已知边界（实测踩到，不是推测）**：判据会读 `snippet`，而摘要里出现查询词不等于**条目**在讲这件事。实测「2026 年某某事件进展」最终由一条 Wikipedia 条目（标题《2026年3月中國大陸》，摘要恰好含全四个词）满足了覆盖度并停在 L0，而那一层其余 14 条全无关。所以这条判据**降低了概率，没有根除**。测试 `已知边界: 摘要里凑齐查询词就能骗过覆盖度` 锁住了这个事实，防止后人以为问题已解决。
- 每次新增判据都让 `stoppedBecause` 变长（现在是 7 条判据的拼接）。它仍然可读，但若继续加，需要改成结构化输出。
- `minQueryCoverage` 是 `RecallContext` 的新字段，默认 0.5。调用方若想要更严/更松可以覆盖。
- 覆盖度是**字面**判据：它证明"这些字都出现了"，不证明"这条在回答这个问题"。它挡掉的是"只匹配一个词的无关结果"这一大族，不是全部。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **122 tests / 122 pass / 0 fail**
- 判据有测试：`覆盖度判据复现真实失效`（断言 1/4 必须判否）、`覆盖度判据不误伤`（断言真实命中放行、`@codemirror/lang-rust` 必须判否）、`单查询词豁免`、`已知边界: 摘要凑词能骗过`
- **线上实测（改动前后对比，同一组 9 个查询）**：
  - 改动前：`{"0":8}`  8/8 全停第 0 层
  - 改动后：`{"0":6,"1":3}`  3 个查询下降到第 1 层
  - 「某国内小众框架的配置怎么写」现在**明确失败**在 `query-coverage`（最佳 2/5）并下降到第 1 层，而不是假装答上了
  - 「Rust 借用检查器怎么用」「React 服务端组件原理」下降到 L1 并由掘金给出中文命中
- **修复过程中测试抓到两个真 bug**：IETF 的 `exact` 精确命中算出来却没拼进返回值；覆盖度比较大小写敏感导致真实命中被判成未覆盖。两者都有测试锁定。
- RFC 编号精确查找顺带落地：「RFC 9110 是什么」首位从 MDN《什么是 URL？》变成 `RFC 9110: HTTP Semantics`（编号是坐标，不经检索）。
