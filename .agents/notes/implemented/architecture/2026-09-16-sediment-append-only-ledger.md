# Agent Note: 沉淀层以「只追加账本 + 可全量重建索引」为唯一形态

Status: implemented

- 影响: `components/HX-Sagasu/src/{ledger,index-store,tokenize}.ts`, `components/HX-Sagasu/scripts/ingest-truth.ts`

## Problem

HX-Sagasu 的第四个目标是"把检索结果沉淀为可复用、可全量重建、带版本身份的数据资产"，已确认规则给了两条硬约束：派生索引必须可全量重建、带版本身份、不符即重建；全文检索索引与查询必须共用同一分词函数。

现状是 argo 的 `--archive` 只写 run 级**不可变快照**，没有可重建的派生索引、没有身份串、也没有跨会话可检索面。更具体的一个损失：`research-output/hx-sagasu/engine-status/*.json` 里的引擎四态判定是每次发布刷新的可观测数据，但它只是一个躺在目录里的 JSON  **下一次会话不会知道"小红书在 2026-09-16 是依赖缺失而非无内容"**，于是同一件事会被重新踩一遍。

从零建这一层时有三个决策点容易走反：

1. **账本能不能改。** "发现写错了就改一下"是最自然的冲动。
2. **索引该怎么跟账本保持一致。** 增量化（只更新变化的部分）性能上显然更优。
3. **身份摘要该拿什么算。** mtime、条数、还是内容？

## Decision

**只追加账本 + 全量重建索引 + 内容寻址身份，三条都是硬约束。**

1. **Ledger 只追加**：`append` 遇到同 id 是 **no-op，不是覆盖**。要改内容只能作为新卡追加已发布的引用必须永远指向同一段原文，否则引用链断裂。
2. **id 是内容寻址**：`sha256(platform|threadId|turnId|quote)`，刻意**不含** `retrievedAt`/`fetchedBy`同一段原文被两个 agent 各抓一次仍是同一张卡，去重不需要额外状态。
3. **索引只有全量重建这一条路径**：不存在"增量更新"入口。身份 = `{indexFormatVersion, tokenizerId, embedderId, sourceDigest}`，`loadOrRebuild` 打开时逐项比对，任一不符即重建。**判断被收进这个函数里，就不可能被调用方忘记。**
4. **sourceDigest 只由卡 id 排序拼接算出**，不用 mtime（只读挂载/复制会丢）、不用条数（一进一出察觉不到）。
5. **分词只有一份实现**（`src/tokenize.ts`），索引侧与查询侧共用。带 `TOKENIZER_VERSION` 进身份。

配套：`scripts/ingest-truth.ts` 把引擎四态真值表里**非 ok 的行**各沉淀成一张可被人读懂的证据卡（ok 是常态、记它只会淹没异常）。

## Alternatives considered

- **账本允许更新/删除**：最符合直觉，也能立刻修正"写错的卡"。否决理由：证据一旦可变，任何引用都不再可信今天引用的话明天可能被改成别的。这与整个系统的前提（"可核查"）直接冲突。
- **索引增量更新**：性能上压倒性地优，尤其当 Ledger 增长后。否决理由：一旦允许增量修补，索引就会长期偏离真相而无人察觉存量里混着旧分词口径的条目，查不到东西却不报错。这正是"必须全量重建"这条规则要防的失效模式；而全量重建的成本在本地千级卡上是毫秒级，代价不对称。
- **用文件 mtime / 条数当身份摘要**：实现一行搞定。否决理由：mtime 在只读挂载与复制时丢失/变化，会造成"该重建时没重建"与"不该重建时狂重建"两种错误；条数在一进一出时完全察觉不到内容变化。
- **把 tokenizer 直接 import 自 HX-Memory 的 `kernel/cjk.ts`**：真正消除重复实现，且它已经是"全仓库唯一文本→词集实现"。否决理由：两组件语料与演进节奏不同，共享版本号会让一方改动强制另一方重建索引；且引用会跨越组件边界形成隐式耦合。折中：算法与不变量照抄并注明出处，**身份独立**；若 HX-Memory 将来把 tokenizer 作为公开端口导出，本文件应改为引用它。
- **把 ok 的引擎也沉淀成卡**：数据更完整。否决理由：ok 是常态，166 个引擎的成功记录会瞬间淹没 7 条异常记录，检索信噪比崩塌。"记住异常"才是这里的价值。
- **在索引层做短语/邻近查询**：更接近真正的全文检索。否决理由：当前索引是有序倒排表，做短语查询需要位置信息，索引结构与重建契约都要跟着改；而现阶段的需求是"跨会话找到相关证据卡"，候选生成 + 上层精排已经够用。属未来工作，不是遗漏。

## Consequences

- 卡片内容不可变：发现记错了只能追加一张新卡（并可用 `supersede` 语义关联），存量卡保持原样。
- 索引每次源变化都全量重建。当前（十级卡）成本可忽略；卡量上千后需要实测重建耗时**这是已知的待测点，不是已验证的结论**。
- `ingest-truth.ts` 需要显式传 `--out`；默认路径相对 cwd，从仓库根与从组件目录调用会写到不同位置。当前由调用方负责传绝对路径。
- 查询是**候选生成器**（OR 语义 + 词权重累加），不保证精度：高频虚词（"的""一"）会产生低分噪声。测试因此断言"新卡可见且排第一"，而不是"结果只有一条"排序归上层。
- 同义归一目前**双向成立**（索引侧展开 + 查询侧展开），但表是硬编码的，会随领域增长需要维护。
