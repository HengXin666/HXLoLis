## Problem

上一轮结束时我写明下一步：**"加可观测性（每来源进入/落定时间戳），别再靠排除法猜差异"**。

而**本轮我又用了 5 轮排除法**才想起去做那件我上轮就决定要做的事。
**这是明确的自我违背**  记在这里，因为它比技术问题更值得记。

## Decision

### 一、新增 `source-started` 事件

`RecallEvent` 此前**只有 `source-settled`**（带 `elapsedMs`），而 `elapsedMs` 是
**从这一层开始算**的  **它把排队时间也算进去了**。

实测：某个来源 `elapsedMs=33028`，而它的**真实网络耗时只有 975ms** 
**其余 32 秒全在闸门后面排队**。

> **"这个来源慢"与"这个来源在排队"是最常被混淆的两件事。**
> 有了进入时刻，两者一对比就能分开。

### 二、`--explain` 输出时间线

```
● t1 juejin                           █                            10869ms  3 条
● t1 bilibili                         █                            10938ms  3 条
✖ t1 bilibili_hot                     ██████████████████████████   25558ms  argo 请求超时
…
排队超过 3 秒的来源（它们本身不慢，是在闸门后面等）:
  wikipedia  总 10489ms / recall 报 10489ms
```

**时间线立刻暴露了一件事**：9 个失败来源的 `settledAt` **完全相同（25558ms）**。

### 三、由时间线推出的修复：握手失败不缓存

那 9 个失败报的 `id` **全是 1**（`initialize` 的 id）。**它们是同一个 Promise 的同一次拒绝，被报了 9 次。**

`readyPromise` 一旦被缓存就**永久缓存**  包括它 rejected 的情况。
于是 `initialize` 超时一次之后，**后续每个 `call` 都立刻收到同一个死 Promise**，**永远无法恢复**。

**修法**：失败时把 `readyPromise` 置回 `null`。

**实测证据（修复前 → 后）**：
```
修复前: 11 个失败，id **全是 1**
修复后:  3 个失败，id 各不相同（1 / 10 / 11） 说明每次握手都是真的重试
```

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **给握手加即时重试**（失败就立刻重发）：看起来最直接。**实测否决**  它让一次召回从 **25s 变成 175s**（每个失败都要等满 15 秒握手超时）。改为**"置 null 但不立即重试"**：让**下一次**（而不是同一个调用）有机会重试。
- **只加事件，不做 `--explain`**：省掉一个 CLI 开关。**否决理由**：**事件是给程序的，时间线是给人看的**。而这件事（区分慢与排队）恰恰是**人看才有效**  程序拿不到"正常应该多快"这个基准。
- **把时间线做成默认输出**：更方便。**否决理由**：它是**诊断视图**，不是结果的一部分。默认输出应该只有结果；诊断要显式要（`--explain`）。
- **时间线用真实墙钟时间而非相对时刻**：更"精确"。**否决理由**：**相对时刻才能看出"哪些是同时的"**  而那正是这次的关键（9 个同时落定 = 同一个 Promise 的拒绝）。绝对时间戳反而要人做减法。
- **把 `elapsedMs` 改成"纯网络耗时"**（不含排队）：语义更"干净"。**否决理由**：**排队时间对用户是真实成本**  他等的就是那个时间。正确做法是**两个都报**（这正是本轮做的），而不是把一个换成另一个。

## 仍未解决的问题

**11 个握手超时仍会在 CLI 路径下出现**（修复只把"同一个死 Promise 被报 11 次"变成"3 个真失败"）。

**本轮新排除的**（在上一轮 7 个方向之外）：

8. **闸门并发控制**  实测 8 个并发经闸门后落定时刻**依次错开**（1327/1975/2082/2594/6111/6940/8248/8443ms），**闸门完全正常**
9. **纯串行**  12 个串行**只失败 1 个**（`reddit`，它本就无后端）
10. **空闲后调用**  建会话后**空闲 11 秒**再串行调用，**6/6 全成功**（模拟 CLI 的第 0 层耗时）

**所以：串行正常、闸门正常、空闲正常，而 CLI 路径下仍有 11 个握手超时。**
**"同一套模块、不同调用形态、结果差 2.5 倍"这个事实仍未解释。**

**下一步该做的（这次真的要按这个做）**：
把 `--explain` 的**时间线输出**在 CLI 与手工脚本上各跑一次，**逐行对比**。
本轮已经做出了这个工具，而**还没有用它做那次对比**  那是下一轮的第一件事。

## Consequences

- **`--explain` 是常驻能力**（不是每次写临时脚本） 这是本轮**确定的收益**。
- **`source-started` 是 `RecallEvent` 的一部分**  界面也能用它画"来源什么时候开始的"。
- **握手失败不再被永久缓存**  减少了一个"一次超时毁掉整场"的故障模式。
- **11 个握手超时的根因仍未定位**。
