# Agent Note: 端到端链路测试  补上"没有一条测试走完完整路径"的缺口

Status: implemented

- 影响: `components/HX-Sagasu/tests/e2e-pipeline.test.ts`（新建，6 条）

## Problem

实测各测试文件的交叉覆盖：

| 测试文件 | `planFetchers` | `sinkHits`/`sinkThread` |
|---|---|---|
| `fetchers.test.ts` | **15** | **0** |
| `sink.test.ts` | **0** | **19** |
| `index-store.test.ts` | 0 | 0 |

**每个部件都有自己的测试，而没有任何一条测试走完这条链。**

**这正是本项目反复栽的坑**：

| 轮次 | 症状 |
|---|---|
| 第 16 轮 | `resolve` 核心场景坏了 16 轮  "测试验证各部件，没有一条走完完整路径" |
| 第 23 轮 | `loadOrRebuild` 零调用方 |
| 第 24 轮 | `url-safety`/`readability` 零调用方 |
| 第 26 轮 | `normalize` 的归一结果没进关键路径 |

**目标第 (4) 项要的"可复用、可全量重建、带版本身份的数据资产"是一条链**，
不是五个部件。**这组测试锁住的是链本身。**

## Decision

**新建 `e2e-pipeline.test.ts`，六条测试各锁住链上的一段：**

1. **组装后的取数表能真的喂给 `recall`**  看似显然，但这正是"各部件都有测试而链断了"
   的最常见形态：`planFetchers` 的输出形状与 `recall` 的入参形状**必须真的兼容**。
2. **召回结果能沉淀进账本**  且 `ledger.size === appended`。
3. **账本能建索引，索引能反查回卡片**  **反查回来的 `cardId` 必须在账本里真实存在**
   （这是"指针有效"的定义），且要能说出 `matched`（为什么被召回）。
4. **索引过期能全量重建，重建后反查结果一致**  这是"可全量重建"的核心验收：
   **账本是真相，索引是派生品**，重建后结果必须与首次**逐条一致**。
5. **对话证据与检索证据进同一个账本**  第 (3) 与第 (4) 项的交汇点：
   帖子证据与检索证据**是同一类资产**，该被同一个索引检索到。
6. **幂等  同一链路跑两次，账本与索引都不变**  且 **`sourceDigest` 相同**，
   那正是"可全量重建"的定义。

## 我做了变异检验（这是本轮最有价值的一步）

**写测试断言容易，但"测试真的在验证什么"必须用变异检验确认。**

### 第一次变异：失败的检验

我把 `sourceDigest` 里的 `ids.sort()` 改成 `.sort().reverse()`  **测试仍然全绿**。

**原因**：排序反转后，两次跑出的顺序仍然相同，摘要自然相同。
**这个变异干扰不了它要验证的性质**  也就是说我第一次选的变异**无效**，
不能据此判断测试好坏。

### 第二次变异：成功的检验

我把 `quoteOf` 改成**返回固定值**（破坏内容寻址）。结果 **8 个测试红了**，
其中 **2 个是端到端测试**：

```
✖ 端到端: 账本能建索引，且索引能反查回卡片
✖ 端到端: 对话证据（帖子）与检索证据进同一个账本
✖ quote 取 snippet  它是来源给出的原文片段
✖ 同 URL 但内容变了 → 是**另一张**卡（内容寻址的意义）
… 共 8 条
```

**这证明这组测试真的在验证内容寻址，不是空转。** 恢复后立即全绿。

> **变异检验的价值不只是"确认测试有效"，更是"确认你选的变异有效"** 
> 第一次那个变异即使测试是空的也会通过。

## Alternatives considered

- **不写这个文件，靠现有 15 个测试文件的 260+ 条测试**：数量上已经很多。**否决理由**：**数量不等于覆盖链**。实测已经证明 `planFetchers` 与 `sink` 分处两个文件、互不相见。而"链断了"正是本项目栽过四次的那个坑。
- **把端到端断言塞进现有文件**（如加到 `sink.test.ts`）：少一个文件。**否决理由**：`sink.test.ts` 的职责是"**卡片构造正确**"，而"整条链通不通"是**另一个关注点**。混在一起会让两个关注点的失败互相掩盖  而**单独一个文件的名字本身就是文档**（`e2e-pipeline`）。
- **端到端用真实网络**（真的调 argo）：更接近生产。**否决理由**：**那会让测试依赖网络与配额**（GitHub 10 次/分已实测撞过），且失败原因无法区分"代码坏了"与"上游限流"。改用受控的假取数器  **它仍走完链的每一段**（形状、序列化、身份比对、内容寻址都是真的），只把"取数"这一步换成确定的输入。
- **不做变异检验**：写完测试就收工。**否决理由**：**那正是本项目栽过的方式**测试全绿而功能是坏的（第 16 轮）。变异检验是**唯一能证明"测试在验证什么"**的手段。**第一次变异失败恰恰说明这个手段是必要的**：我本来会以为测试没问题。
- **把第一次那个失败的变异当成"测试无效"的证据**：顺着它去改测试。**否决理由**：**错的不是测试，是变异选得不对**。`sort().reverse()` 不改变"两次运行结果是否相同"这个性质。**判据选错会导向错误的修复**（这与第 25 轮"按 platform 去重看不见 X.com 重复"是同一族）。

## Consequences

- **测试总数 255 → 261**。
- **`e2e-pipeline.test.ts` 是"链"的守卫**  未来任何让链断掉的改动会在这里红。
- **未做**：真实网络路径的端到端（见上，刻意不做）。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **261 tests / 261 pass / 0 fail**
- **变异检验（有效）**：`quoteOf` 返回固定值 → **8 条测试红**（含 2 条端到端），
  恢复后立即全绿
- **变异检验（无效，记录在案）**：`sourceDigest` 排序反转 → 测试仍绿 
  **这是变异选错，不是测试无效**
