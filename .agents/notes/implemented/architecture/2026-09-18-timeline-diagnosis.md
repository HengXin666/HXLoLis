# Agent Note: 用时间线定位并发失败  进展与仍未闭合的部分

Status: implemented

Decision-ID: timeline-diagnosis

- 起点: 上轮结论"下一轮第一件事是用 `--explain` 逐行对比两条路径"

## Code

- `components/HX-Sagasu/scripts/sagasu.ts`

## Problem

上轮我做出 `--explain` 时间线，并写明下一步是**用它对比** CLI 与手工脚本。
本轮照做了  **而时间线让问题从"10 个模糊的失败"收窄到一个具体现象**。

## Decision

### 时间线给出的关键读数

```
✖ t1 bilibili_hot   进入 +10584ms  落定 +25596ms
✖ t1 baidu_baike    进入 +10584ms  落定 +25596ms
✖ t1 reddit         进入 +10584ms  落定 +25596ms
… (共 9 个，进入与落定时刻**完全相同**)
```

**9 个来源在同一毫秒进入、同一毫秒落定。**

**但这不再是"闸门失效"**  本轮用假 session 直接测了并发数：

```
10 个并发经 argoFetchers | 总耗时 302ms | **最大并发 1** ✅ 闸门完全生效
```

**所以那 9 个是"同时进入队列"，而不是"同时执行"。**
`source-started` 发在 `await fetch()` 之前，而闸门在 `fetch` 内部 
**它记的是"进入队列"的时刻，不是"拿到闸门"的时刻**。

### 由此修正的一个认知

上轮我把"9 个同时落定"读成"闸门没拦住"。**那是误读** 
正确读法是"9 个同时排队，然后被串行处理，而**它们全部失败了**"。

### 本轮用真实 argo 直接测队列行为（12 个并发经闸门）

```
juejin       进入 +0  落定 +1620  ok
bilibili     进入 +0  落定 +2156  ok
…
huggingface  进入 +0  落定 +13164 ok
reddit       进入 +0  落定 +21165 FAIL   ← 它本就没后端
```

**11 成功 / 1 失败，落定时刻依次错开。闸门与串行都正常。**

### 本轮新排除的 4 个方向（累计 14 个）

| # | 方向 | 实测 |
|---|---|---|
| 11 | **模块重复实例** | 同一说明符两次导入 → 同一实例 |
| 12 | **闸门并发数** | 假 session 测最大并发 = **1**（完全串行） |
| 13 | **`try/finally` + `ctx.session.close()`** | 加上后 70.1s/4 失败（与无 finally 一致） |
| 14 | **真实两阶段时序**（完整第 0 层 10.5s → 第 1 层） | **8 成功 / 1 失败** |

**第 14 项最关键**: 我完整模拟了 CLI 的时序（真实第 0 层跑满 10.5 秒），
而第 1 层的 9 个 argo 来源**成功 8 个**。

**所以我至今无法在受控条件下复现那个失败**  它只在 `literal.mjs` / CLI 这两个具体文件里出现，
而它们的代码与受控实验**实质相同**。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **继续分解 `literal.mjs`**（逐块替换成受控版）：本轮已做 4 次分解（`v3`/`v4`/`v5`/`v6`），**每次都得到"正常"的结果**。**否决理由**：**当受控复现总是成功、而目标文件总是失败时，继续在"代码差异"上找原因是低期望的**  差异可能根本不在代码里（进程启动环境、模块加载顺序、argo 侧的状态）。
- **把 `literal.mjs` 当成"不可复现"而不记录**：省事。**否决理由**：它**稳定复现 3/3 次**（21.6s / 25.4s / 19.4s，恒为 10 失败）。**稳定复现的东西不该被当作噪声。**
- **加即时重试让失败自愈**：上轮已实测否决（25s → 175s）。
- **继续投入**：**否决理由**：本轮 8 轮 + 上轮 13 轮 = **21 轮**，而**新排除的每一条都指向"代码没问题"**。**这已经不是"再查一层"能解决的**  需要的是**换工具**（如给 argo 子进程的 stdin/stdout 加原始帧日志，看那 15 秒里到底发生了什么）。

## Consequences

- **`--explain` 被证明是有效的排障工具**  它把"10 个失败"变成"9 个同时进入同时落定的具体现象"。
- **一个认知被修正**：`source-started` 记的是"进入队列"而非"拿到闸门"  这个区别值得写进它的注释（**本轮已补**）。
- **14 个方向已排除**，且**每一个都有实测数据**。
- **失败仍未根因化**。它的实际影响：**第 1 层的 argo 来源覆盖率下降约 10/12**，但**不影响可用性**（三个查询均 `exit=0`、第 0 层完整、命中 15-24 条）。
