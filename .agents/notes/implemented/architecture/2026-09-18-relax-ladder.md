# Agent Note: 放宽阶梯  精准查询归零时不该到此为止

Status: implemented

Decision-ID: relax-ladder

- 上游: 精读 argo `recovery.py` 的 `structured_relax_steps`（`recovery.py:152`）

## Code

- `components/HX-Sagasu/src/recall.ts`

## Problem

我们有几种**平台原生语法**（不是我们发明的抽象，是平台边界的直接映射）：

- Telegram `<频道名> <关键词>`（频道内搜索，`adapters/telegram.ts:165`）
- 通用减号 `关键词 -排除词`（本轮刚加的否定约束）
- 引号短语 `"精确短语"`

**这些语法越精准，归零的概率越高。** 而我们现在归零时**什么都不做** 
调用方写 `durov telegram` 拿回 0 条，就到此为止了。

argo 的 `structured_relax_steps` 解了这个问题：**每步只撤一类条件，
从"最不损失意图"的那类开始撤**。它的顺序是「排除 → 热度 → 媒体 → 语言 → 日期 → 账号 → 短语」
越靠前撤掉，对用户意图的损失越小。

## Decision

**实现两层阶梯，顺序按"损失从小到大"：**

1. **撤减号排除**（损失最小） 用户排除某词多半是"不想要但也能接受"，撤掉后查询变宽，最可能拿到结果。
2. **撤引号**（损失中等） 精确短语是强约束，撤掉后词还在，只是不再要求连续。

**刻意不实现第三层（撤频道作用域）**：那会改变**查哪个来源**，不是改变查询。
把一个来源的失败变成另一个来源的请求，语义不同，必须由调用方决定。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **照搬 argo 的七层阶梯**：它经过实测调优。否决理由：**它的七层对应它支持的七类平台语法**（X 的 `min_faves:`、GitHub 的 `repo:`、Reddit 的 `subreddit:`…），**我们只有三类**。照搬会产出四个永远为空的步骤  界面上显示"试了 7 种策略"，实际只有 3 种存在。**那是假的能力，比没有更坏**（它让人以为已经尽力了）。**阶梯的层数必须等于真实支持的语法数。**
- **把阶梯做成"自动在 recall 内部重试"**：调用方无感，最省事。否决理由：**那会让"归零"这件事被静默掩盖**。我们的契约是"失败必须可见"，而自动重试会让调用方永远不知道原始查询是坏的  它只看到"有结果"。**阶梯必须由调用方显式驱动**，且每一步的结果要能报出来。
- **无语法可撤时返回原查询**：让调用方逻辑更简单（总是拿到至少一个候选）。否决理由：**返回原查询等于"重试同一个查询"**，而它刚刚才归零  这是纯粹的浪费，且会让调用方以为"试过了"。改成返回 `[]`，语义是"没有可撤的东西"。
- **同时实现 argo 的 L2 同义词替换**：能显著提高召回。**本轮没做**  它需要一份同义词表，而**没有实测支撑的同义词表会引入错误召回**（把"苹果"替换成"Apple"在水果语境下是错的）。要做就得先有可验证的词表，那是独立一件事。
- **实现 argo 的 L3 换引擎**：我们确实有 26 个来源可换。否决理由：**我们的架构里"换引擎"已经是内建的**  分层下降本身就是这个机制（第 0 层不够就下到第 1、2 层）。再叠一层"同层内换引擎"会与分层语义重叠，且难以说清两者的边界。

## Consequences

- **`relaxSteps` 是纯函数**，不碰网络、不改状态  调用方拿到的是一串**完整可用**的查询，按顺序试，首个非空即停。
- **未接入 recall 主流程**：它需要调用方显式驱动（见上）。CLI 与界面会在下一步接上，届时"归零 → 放宽 → 重试"的每一步都会作为事件报出来。
- **未做**：同义词替换（L2）、换引擎（L3）、跨语言回退（L4）。
