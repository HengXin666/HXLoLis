# Agent Note: 错别字容错必须进检索词  第五次"机制在、没接线"

Status: implemented

Decision-ID: normalize-must-reach-query-terms

- 相关: `src/normalize.ts`（实现未变，其归一结果**此前从未进过检索词**）

## Code

- `components/HX-Sagasu/src/recall.ts`

## Problem

目标第 (3) 项要求"错别字容错"。`normalize.ts` 完整实现了它 
混淆词表（23 条）、自我更正（"不对，我是说…"）、口头填充词、**变体集**，
文件头甚至写着"做意图判定与检索时必须先做容错归一"。

**而它只被用在意图判定上**（`recall.ts:440`，`classifyQueryIntent`），
**检索词抽取用的是原始查询。**

实测缺口：

| 查询 | `normalize` 产出 | 但 `queryTerms` 抽的仍是 |
|---|---|---|
| `微薄 热搜` | `微博 热搜` | **`["微薄","热搜"]`** |
| `知呼 怎么学 Rust` | `知乎 怎么学 Rust` | **`["知呼",…]`** |
| `那个那个 就是就是 编成语言` | `编程语言` | **`["那个","就是","个那","是就","编成"]`** |

搜"微薄"去匹配含"微薄"的文档，而不是"微博"  **容错能力做了，等于没做。**

**这是同一形态在本项目第五次出现**：

| 轮次 | 模块 | 症状 |
|---|---|---|
| 第 16 轮 | `resolve` | 核心场景坏了 16 轮没人发现 |
| 第 23 轮 | `index-store.loadOrRebuild` | 零调用方 |
| 第 23 轮 | `resolve` | 零调用方 |
| 第 24 轮 | `url-safety` / `readability` | 零调用方 |
| 本轮 | `normalize` 的归一结果 | **有调用方，但结果没进关键路径** |

第五次比前四次更隐蔽：它有调用方（意图判定用了），所以 grep 调用方**看不出来**。

## Decision

**`queryTerms` 三步串起来：先归一容错 → 再剥否定片段 → 最后抽词。**

三步各有实测依据：

1. **归一**（本轮加）: 错别字/同音字/口语句读
2. **剥否定片段**（第 21 轮加）: `除了`/`不要`/`not` 这些触发词**必然出现在查询里**，
   不剥掉就会让任何含这些字的文档被判为"覆盖了查询词"
3. **抽词**（词流 + CJK bigram）: bigram 保证"2 字查询与未登录词可召回"

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **把 `normalize` 的 `variants` 也并进检索词**（"两种写法并列搜"）：文件头正是这么写的（"检索时应当**并列搜索**的写法"）。否决理由：**那会把容错变成"两种写法都算命中"**  一条**只含错字的旧文**（"微薄的实时热搜榜"）就成了相关证据，判据失真。**容错的正确形态是用归一后的词去检索，而不是把错字也当有效词。** 已加测试显式锁住这条。
- **在 `recall` 里对归一前后各搜一次**：最彻底，能同时命中错字文档与正确文档。否决理由：**查询次数翻倍**（26 个来源 × 2），而收益仅覆盖"文档标题也打错字"这一个场景。当前取舍（归一后搜一次）在**两种场景下都不丢证据**（见下），只是错字文档的排序靠后。**用 2 倍请求换一个排序改善，不划算。**
- **只改检索侧，不改判定侧**：只影响"用哪些词去搜"。否决理由：`queryTerms` **同时被检索与判定使用**（第 18 轮的教训: "两处共用这一个函数，口径不允许漂移"）。只改一边会造成"搜到了但判为不相关"。
- **把归一写进 `termStreams`**：更底层，所有调用方自动受益。否决理由：`termStreams` 是**分词**（`tokenize.ts`），而"错别字纠正是**归一**"（`normalize.ts`） 两者职责不同。塞进分词层会让"分词器"这个概念包含改写，而**索引侧与查询侧必须共用同一分词函数**（已确认规则 `r45fbf1463ba24cf8`） 一旦分词器开始改写，账本里已沉淀的卡片的索引口径也会变，触发全量重建。**这是不必要的连锁反应。**

## 关于"文档标题也是错字"的退化（实测权衡）

修复后实测两个方向：

| 场景 | 覆盖数 | `isQueryRelevant` |
|---|---|---|
| 查询 `微薄 热搜`，文档标题 `微博热搜榜`（对的） | **2** | true |
| 查询 `微薄 热搜`，文档标题 `微薄的实时热搜榜`（也是错字） | 1 | **true** |

第二行相对修复前**退化了一个词**。**但这是可接受的取舍**：

- 判据 `isQueryRelevant` 只要 **≥ 1 个词**，所以**两者都进相关组**
- 退化的只是**组内排序**，**证据没有被丢掉**

> 修复前是"错字文档覆盖 2 个词、正确文档覆盖 0 个词"（完全反了）；修复后是"正确文档 2、错字文档 1"。
> **从"完全反了"变成"都对，只是排序不同"。**

## 一个我自己犯的断言错误

新测试里我写了 `assert.deepEqual(queryTerms('React 服务端组件原理').slice(0,3), ['react','服务','端'])`

（"服务端"被切成 `服务` + `端组` + `组件`，正是文件里记着的 `Intl.Segmenter` 词典缺陷）。

**测试断言必须照着实测写，否则测的是我的想象。** 改成用 `includes` 断言关键项存在。

## Consequences

- **`queryTerms` 的口径变了**：带错别字/填充词的查询，其检索词集合会变成**归一后**的。
  这会**同时影响**排序（`isQueryRelevant`）与充分性（`queryCoverageSignal`）
  两处共用这一个函数是刻意的（口径不允许漂移）。
- **索引侧不受影响**：`tokenize.ts` 未动，所以已沉淀卡片的索引身份不变，**不触发重建**。
- **未做**：变体集并列检索、"文档也打错字"的兜底路径。
