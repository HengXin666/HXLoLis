## Decision

### 一、验收通过的部分：不动

### 二、发现一个真实缺陷，但**修法被实测否决，故回滚并记录**

验收时看到 `话题词: "法对"`  那是 `楼上的说法对吗` 被**逐字**剥词后的碎片。

`extractTopic` 的最后一层是**单字**替换（`的`/`说`/`吗`），于是:

```
楼上 [空] [空] 法 [空] 对 [空]   → 两个不相邻的残字被拼成 "法对"
```

**我改成「按原词边界切分」**（`split(/\s+/)` 后整词判停用词）。**实测更糟**:

| 查询 | 改前 topic / floors | **改后 topic / floors** |
|---|---|---|
| `楼主后来改口了吗` | `改口了` / 2 | **整句** / 2 |
| `楼上的说法对吗` | — | **整句** / **0** ← 退化 |

**原因**: **中文提问没有空格**，`split(/\s+/)` 把整句当成**一个 token**，
停用词表一个都不命中 → 剥不掉任何东西 → `relevantFloors` 从有值变成 0。

**已回滚**，并在代码里留下完整的缺陷描述与这条否决记录。

## Alternatives considered

- **改用 `tokenize.ts` 的分词**：那是真正的分词器，不会切出碎片。**否决理由**：
  它是**索引侧**的分词（词流 + CJK bigram），而 `topic` 只用于**排序**、
  **不影响证据是否返回**（有测试锁住这条契约）。**收益不足以为它换一套分词口径** 
  换口径意味着两处分词可能不一致，而那正是本项目反复栽过的坑。
- **保留我的「按词切」改动并改那条测试**：让测试迁就实现。**否决理由**：
  **那条测试记录的是实测行为**，而我的改动让 `relevantFloors` 从有值变成 0 
  **那是功能退化，不是测试过时**。改测试会把退化固定下来。
- **保留改动但加回退**（切不出就退回逐字）：两者兼得。**否决理由**：
  **那会让行为依赖输入形态**（有空格走一条路、没空格走另一条），而两种路径的
  `topic` 语义不同。**复杂度换来的收益是 0**  因为 `topic` 只影响排序。
- **什么都不做，也不记录**：最小。**否决理由**：**下一个看到 `"法对"` 的人会是我的同一条路**。
  记录两次否决让那一轮不必重走。
- **把 `楼上的说法对吗` 的 `relevantFloors=0` 也当成 bug**：更彻底。**否决理由**：
  **那是原有行为，与本次改动无关**。而按上面第一条的判据，`topic` 只影响排序 
  `floors=0` 意味着「这个话题词在这条帖子里没有对应楼层」，**那可能就是事实**。

## Consequences

- **全链路验收通过**  四条需求串起来能跑通，包括需求 (4) 的身份重建规则。

  **但它不影响证据返回**。
