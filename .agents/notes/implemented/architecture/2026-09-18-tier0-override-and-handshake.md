# Agent Note: 第 0 层被 argo 覆盖 + 握手计时器起点错  以及一个未解决的差异

Status: implemented

Decision-ID: tier0-override-and-handshake


## Code

- `components/HX-Sagasu/src/fetchers.ts`

## Problem

从"CLI 在 `--min-hits 40` 时 11 个 argo 来源报 `method=initialize` 超时"开始查。

### 发现的第一个真 bug：第 0 层的 `wikipedia` 被 argo 实现覆盖

`planFetchers` 的"argo 整层补齐"（`fetchers.ts:322`）只避让 `claimed`，
而 `claimed` **只记录 `SOURCE_PLAN` 的 primary**。

`wikipedia`/`hackernews` 的 argo 那条登记为 **fallback**（它们的 primary 是
authoritative 的原生 HTTP），于是**它们不在 `claimed` 里 → 被整层补齐覆盖成 argo 实现**。

**实测证据**：修复前它们报 `[argo/network]`，修复后报 `[web/network]`（原生 HTTP）。

**危害**：第 0 层的权威来源走了 argo  慢（串行）、且**顶掉了原生实现**。

**修法**：判据从"已认领"改为"**在 `SOURCE_PLAN` 里出现过**"
无论 primary 还是 fallback，它的实现都必须由 `SOURCE_PLAN` 决定。

### 第二个真 bug：握手计时器的起点错

`ready` 在**会话创建时**就发出 `initialize` 并挂上 15 秒计时器。而实测：

```
第 0 层耗时 10.5 秒（wikipedia 网络超时占大头，它不走 argo）
→ 等第 1 层真正要用 argo 时，计时器已流逝 10.5 秒
→ 只剩 4.5 秒给握手，稍有波动就超时
→ 11 个等待者**全部收到同一个 reject**（它们 await 的是同一个 Promise）
```

**修法**：握手**懒发**  计时器与"谁在用"同步起算。

## Decision

### 一、整层补齐必须避让**所有已登记的来源**

判据从"已认领"（claimed）改为"**在 \`SOURCE_PLAN\` 里出现过**" 
无论 primary 还是 fallback，它的实现都必须由 \`SOURCE_PLAN\` 决定。
整层补齐只负责"没有任何登记"的那些。

### 二、握手改为**懒发**

计时器与"谁在用"同步起算，而不是从会话创建起算。

### 三、那个未解决的差异**如实记录而不猜测**

见下节。记录它本身就是本轮的决定  因为它可能指向一个更深的非确定性。

## 未解决的差异（诚实记录）

**同样的参数、同样的模块，CLI 与手工复现的结果不同**：

| | 耗时 | argo 失败数 |
|---|---|---|
| CLI（`sagasu search`） | 19-26s | **12** |
| 手工脚本（相同 `planFetchers` + `recall`） | 72s | **4** |

**我没有找到差异的来源。** 排查过的方向（都已排除）：

1. 会话数量  两边都只建 1 个
2. 空闲导致会话失效  实测空闲 12 秒后调用正常（289ms）
3. 闸门是否生效  经 `argoFetchers` 并发 11 个**成功 10 个**，闸门正常
4. 懒发握手  改后仍是 11 个
5. 第 0 层的 `wikipedia` 干扰  修掉后仍是 11 个
6. `adapter` 模块 / `scope-probes` 副作用导入  两者都加上后复现脚本仍只有 4 个失败

**当前状态是可用的**（`exit=0`、24 条命中、第 0 层完整），
但**第 1 层有 11 个 argo 来源白白失败**  那是**真实的能力损失**。

**下一步的方向**（留给下一轮）: 给 `recall` 加一个"每个来源的进入/退出时间"日志，
让 CLI 与脚本的**执行时间线可直接对比**  靠"排除法"猜差异代价太高，
而**时间线是能一次性看到差异的东西**。

## Alternatives considered

**什么都不做 / 复用现有。** 最强理由是无需新增实现和维护成本. 现有状态仍存在 Problem 中的具体缺口, 因此采用本记录的选择

- **把握手超时从 15 秒调大**（如 60 秒）：能"解决"当前症状。**否决理由**：**症状会以别的方式回来**  真正的问题是计时器起点，而不是值太小。而且 60 秒的握手等待会让"argo 不可用"变成一个**要等一分钟才发现**的事实。
- **只修 wikipedia 覆盖，不修握手**：改动更小。**否决理由**：两者是**独立**的问题（一个在组装层、一个在会话层），各修各的。实测证明修前者不改变后者的表现。
- **继续用排除法查那个差异**：更彻底。**否决理由**：**已经花了 8 轮，而每轮排除的都是错误方向**。**换手段比继续猜更值**  下一步该用"时间线对比"而不是继续假设。
- **接受当前状态，不记录这个差异**：省事。**否决理由**：**"同样代码不同结果"必须被记录**  它可能指向一个更深的非确定性（并发时序、会话状态），而那类问题**不记录就会在更贵的场合爆发**。
- **把 11 个失败来源从 `ARGO_ENGINE` 里删掉**：让输出变"干净"。**否决理由**：**那是用删掉问题来伪装解决**。它们是**能用的**（手工脚本里成功），当前失败是**调用层的问题**，不是它们坏了。

## Consequences

- **第 0 层的 `wikipedia`/`hackernews` 回到原生 HTTP 实现**  这是本轮确定的收益。
- **握手不再因"没人用时的等待"而超时**。
- **第 1 层仍有 11 个 argo 来源失败**（未解决，见上）。
- **端到端仍是可用的**：`exit=0`、19-26 秒、24 条命中。

## Verification

- `bash components/HX-Sagasu/scripts/test.sh` → **275 tests / 275 pass / 0 fail**
- **wikipedia 修复实测**：`[argo/network]` → `[web/network]`（走回原生 HTTP）
- **CLI 稳定性**：连跑 3 次，`exit=0`，19.1-25.9 秒，24 条命中，失败数恒为 12
- **闸门验证**：经 `argoFetchers` 并发 11 个 → **成功 10 / 失败 1**（闸门正常）
- **空闲验证**：空闲 12 秒后调用正常（289ms）
- **对比数据（未解决）**：CLI 12 失败 vs 手工脚本 4 失败，耗时 19-26s vs 72s
