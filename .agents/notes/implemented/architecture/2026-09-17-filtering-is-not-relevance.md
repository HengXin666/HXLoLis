# Agent Note: 用过滤表达相关性  一个让核心场景整个失败的错误

Status: implemented

Decision-ID: filtering-is-not-relevance


## Code

- `components/HX-Sagasu/src/resolve.ts`

## Problem

`resolve.ts`（L2 指代消解）落地已久、测试齐全，但**从未被任何非测试代码调用**（全仓库搜 `from './resolve` 零结果）。我去查它为什么没接线，直接拿真实形态的 Thread 跑它**核心场景整个失败**：

```
resolve(thread, '楼主后来改口了吗')  → topic = "改口了"
                                    → relevantFloors 返回 **0 条**
```

而"楼主后来改口了吗"**正是本项目第 (3) 项需求点名的验收判据**（架构方案 §5.2 判据 1：给一个真实论坛帖，问"楼主后来改口了吗"，系统必须回到**具体楼层**并给出原文引用）。

**它不是解析错了**`楼主` 被正确解析到楼层 1 和 3，置信度也对。错的是最后一步：

```ts
// 此前实现
return all.filter(c => overlapCoefficient(bigrams(topic), bigrams(c.quote)) > 0)
```

**它用话题词做硬过滤。** 而 `extractTopic` 从"楼主后来改口了吗"里剥掉角色词与疑问词后，剩下的是 **"改口了"**一个**关于提问动作**的词，不是内容话题。没有任何一楼含"改口了"，于是全部被滤掉。

根子上的错误是**用过滤表达相关性**：过滤会丢掉"不含该词但正是答案"的楼层。而这类问题问的是**随时间的变化**，答案往往恰恰不含问题里的字面词楼主改口后说的是"编译期约束"（或本例的"权重的问题"），不是"改口"。

## Decision

**话题匹配改为重排，不再是过滤。**

```ts
const score = (c: Citation) => overlapCoefficient(bigrams(topic), bigrams(c.quote))
return [...all].sort((a, b) => score(b) - score(a))   // 稳定排序
```

与话题有重叠的楼层排前面，**无重叠的保留在后面**。排序不改变集合，因此一次错误的话题提取不会丢掉证据。

## Alternatives considered

- **什么都不做，让它继续不被调用**：它此前就是这么活着的测试全绿，无人使用。否决理由：这是**第 (3) 项需求的核心能力**，而且架构方案 §5.2 把它写成了可验收判据。让它继续"存在但不可用"，等于用一份绿色的测试掩盖一个未交付的功能。
- **修 `extractTopic`，把"改口了"这类提问动作词也剥掉**：能直接解决这个具体反例，改动最小。否决理由：**剥不干净**。提问语言里表达"变化/求证"的说法是开放集合（改口了、后来呢、还坚持吗、有没有改变主意、态度变了吗……），而每加一个词都在给一个**本来就判不准**的东西打补丁。**真正的错误不是话题提取得不好，而是把它的结果当成了过滤器。** 修 `extractTopic` 会让人以为"提取得够好就不会出问题"，从而保留这个危险的架构。
- **话题为空时返回全部（即保留过滤，只是加个兜底）**：改动更小。否决理由：它只在提取彻底失败时救命，而"提取出一个错的词"才是实测发生的形态。"改口了"不是空字符串，它是一个**看起来合理但语义错误**的话题兜底判据区分不了这两种情况。
- **按相关度排序但丢掉 0 分的楼层**：想让结果更"精炼"。否决理由：**这正是原实现的病换了件衣服**。0 分意味着"字面不重叠"，而"楼主改口了吗"的答案按定义就在字面不重叠的那一楼（不然就不叫"改口"）。丢掉 0 分等于丢掉答案。
- **把 `relevantFloors` 的排序改成一个独立的显式参数**（调用方选择过滤或重排）：更灵活。否决理由：**当前只有一个调用点且它不存在**。给一个没有调用方的函数加模式开关，是在为一个想象中的需求增加真实的复杂度。等真有第二个调用方再说。

## Consequences

- **核心场景修复**：`楼主后来改口了吗` → 证据楼层 `f1, f3`（楼主的两条发言，按楼层顺序）。
- **排序是稳定的**：同分保持楼层顺序。这一点重要`digest` 的注释写着"按楼层顺序而不是相关度排序，因为'后来改口了吗'问的是**随时间的变化**，打乱顺序会让变化不可见"。重排在整个集合上做，但同分不动，所以变化仍可读。
- **加了三项测试**，其中一项**故意断言 `r.topic === '改口了'`**  把实测到的错误行为**钉在测试里**，而不是假装它不存在。它锁住的契约是"即使话题提取错了，证据也不能丢"。
- **`resolve.ts` 仍未接线**（本轮只修了它的正确性）。把"能正确工作"和"被调用"分开，是刻意的：接线需要先决定**它从哪里拿到 Thread**（适配器的 `thread()` 返回 `RawThreadInput`，经 `normalizeThread` 才得到 `Thread`），那是另一个决策。
- **一处契约陷阱仍未消除**：`normalizeThread()` 返回 `{thread, normalizations}` 而 `resolve()` 吃 `Thread`。我第一时间就写错了（`normalizeThread(raw)` 直接传给 `resolve`，报 `Cannot read properties of undefined (reading 'filter')`）。**这个陷阱是静态类型挡不住的**（返回类型是 `NormalizedThread`，不是 `Thread`，本应被 TS 挡住但项目跑的是 `--experimental-strip-types`，不做类型检查）。**"类型对了就不会错"在这里不成立**，值得单独记一笔。
