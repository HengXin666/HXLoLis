# Agent Note: 沉淀覆盖三条路径  以及"证据用原文还是归一文本"

Status: implemented

Decision-ID: sink-all-three-paths


## Code

- `components/HX-Sagasu/scripts/sagasu.ts`
- `components/HX-Sagasu/src/sink.ts`

## Problem

目标第 (4) 项要求"把检索结果沉淀为可复用、可全量重建、带版本身份的数据资产"。

**而此前只有 `search` 会写账本**  `thread` 与 `fetch` 都不写。

代价是具体的：`search` 沉淀的是 **snippet**（可能被截断），
而 `thread` 产出**整楼原文**、`fetch` 产出**完整正文** 
**它们才是更接近"一手证据"的东西，却全部没有落盘。**

## Decision

**给两条路径都接沉淀，并明确"沉淀什么"。**

### 一、`sinkThread`：帖子沉淀

`EvidenceCard` 的字段（`platform` / `threadId` / `turnId` / `quote`）
**本来就是为对话证据设计的**  它的 doc 写着"指向具体某一楼，不是整帖"。

**跳过的两类**（都不改变帖子本身，只跳过沉淀）：

| 情形 | 计数 | 理由 |
|---|---|---|
| 楼层太短（< `MIN_QUOTE_CHARS`=12） | `skippedTooShort` | "沙发"/"顶"/"确实"**不构成证据**，无法支撑任何结论 |
| 没有原文 | `skippedNoQuote` | 异常数据，要能被看见 |

**两类都单独计数并打印**  否则"沉淀了 10 张"与"沉淀了 3 张"看不出差别在哪。

### 二、`sinkFetched`：抓取正文沉淀

**按段落而不是整篇**：卡片是"最小证据单元"，整篇正文作一张卡会让
"**为什么这张卡被召回**"无法回答  而那是索引的 `matched` 字段要的粒度。

`threadId` 用 URL 的 sha256 前 16 位  **同一 URL 的段落归在一条记录下**，
这样能回答"这些段落来自哪一页"。

## 本模块最容易做错的一件事（写进了代码注释与测试）

**`quote` 必须是原文，不是归一文本。**

卡片的契约写着：

> `quote`: 原文字面引用。**不是**归一化后的文本  **证据必须能在源站核对得上**。

而我们在 L1 归一里改了**错别字、繁简、全半角**（`normalize.ts`）
那些改动**让文本更好检索，却让它不再是源站上的原文**。

所以 `sinkThread` 取 `t.text` 而**不是** `t.normalizedText`：

```ts
const quote = String(t.text ?? '').trim()   // 不是 normalizedText
```

**有测试锁住**：喂一个 `text: '视屏压缩工具…模版也全'`、`normalizedText: '视频…模板…'` 的楼层，
断言卡片的 `quote` 含"视屏"（原文）而**不含**"视频"（归一）。

> **归一文本是索引用的，原文才是证据。** 两者混用会让"证据可核对"这条契约失效 
> 而且失效得很隐蔽：**卡片看起来很正常，只是对不上源站。**

## Alternatives considered

- **让 `thread`/`fetch` 复用 `sinkHits`**（把楼层伪装成 `SourceHit`）：省一个函数。**否决理由**：`SourceHit` 的形状是 `{sourceId, title, url, snippet}`，而楼层是 `{platform, threadId, turnId, text}`。**强行映射会丢掉 `turnId`**  而"指向具体某一楼"正是卡片契约的核心（"不是整帖"）。丢掉它，引用链就断在账本里了。
- **`quote` 用 `normalizedText`（归一后的）**：与检索侧口径一致，看起来更"干净"。**否决理由**：**那会让证据对不上源站**。用户拿着卡片里的引文回源站核对时找不到  而卡片存在的全部意义就是**可核对**。**归一提升的是召回率，不是证据质量，两者不该混。**
- **太短的楼层也沉淀**（不做长度过滤）：数据的"完整性"更好。**否决理由**：卡片是**证据**不是**日志**。"沙发"沉淀进去只会让账本膨胀，且让"为什么这张卡被召回"更难回答（它接不上任何结论）。**但那类楼层仍然留在帖子里**（`sinkThread` 不改 `Thread`） **过滤的是沉淀，不是数据**。
- **`fetch` 整篇正文作一张卡**：实现最简单，且不丢任何内容。**否决理由**：卡片是**最小**证据单元。整篇作一张卡意味着索引只能回答"这一页相关"，回答不了"**哪一段**相关"  而 `matched` 字段（索引的审计字段）要的正是后者的粒度。
- **界面也提供沉淀按钮**：功能更完整。**否决理由**：账本是**只追加**的，写错了擦不掉。**沉淀必须走 CLI 的显式 `--sink`**  这与 `2026-09-18-thread-on-ui.md` 里"界面不写账本"是同一条决策。
- **不做幂等检查**（重复沉淀就重复写）：实现更直接。**否决理由**：**幂等是"可全量重建"的前提**  只要能重新取到同样的内容，账本就会收敛到同一状态（`cardId` 内容寻址）。有测试锁住"第二次沉淀是 no-op"。

## Consequences

- **三条路径全部接通沉淀**：`search` / `thread` / `fetch`。
- **`MIN_QUOTE_CHARS` 导出**，两条路径共用同一条判据（口径不漂移）。
- **账本回写失败要说出来**（`✖ 账本回写失败: …`） 副作用失败不能假装没发生。
- **仍未做**：`lensId`（视角）只在 `fetch` 用了（取页面标题），
  `thread` 没传  "同一个帖子在多个研究视角下的复用"还没设计。
