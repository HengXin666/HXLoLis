# 取证: 这个仓库真实会犯什么错

目的是拿到**失败形状**, 不是技术栈清单. 技术栈决定判据的**形状**(用什么解析器), 不决定**清单**

所有命令在仓库根执行. **命令里的 glob 一律加引号**  不加引号在 zsh 下会被 shell 先展开, 不匹配任何文件时直接报错退出(`no matches found`), 而不是把模式交给命令

## 一、规模与改动分布(先跑, 只读)

```bash
git ls-files | wc -l
git ls-files | sed 's/.*\.//' | sort | uniq -c | sort -rn | head -20

# 最大的源码文件(体积热点)
git ls-files '*.py' '*.ts' '*.tsx' '*.vue' | xargs wc -l 2>/dev/null | sort -rn | head -20

# 改动最频繁的文件(高 churn × 大体量 = 最该被结构约束的地方)
git log --since='6 months ago' --name-only --pretty=format: | sort | uniq -c | sort -rn | head -30

# 测试与源码比(接近 0 说明测试还不是可依赖的防线, 别急着加覆盖率门禁)
git ls-files | grep -cE '(^|/)(test_|tests?/|.*\.(test|spec)\.)' || true

# 每一次"修 lint / 修 CI / 回滚"都是一次已发生的失败
git log --oneline --since='12 months ago' -i --grep='revert\|rollback\|fix lint\|lint fix\|fix ci\|fix build\|hotfix\|回滚\|修复门禁'
```

现有防线必须**读内容**, 不能只看存在

- 包管理器的 scripts 段: 有哪些可跑的命令、哪些是摆设
- linter / formatter / 类型检查的配置: 哪些规则被关掉了(`ignore` / `off` / `skip`)
- CI 配置: 有没有 `continue-on-error`、`|| true`、空 job、永不失败的门禁、被注释掉的步骤
- git hook 配置(pre-commit / husky / lefthook): 装了没有、跑什么、耗时预算多少
- 已有的门禁脚本: 有负向探针吗? 白名单陈旧吗(条目对应的代码还在不在)?

## 二、把已经写下来的规则逐条对数(最值钱的一步)

仓库的规范文档里写的每一条约定, 都在告诉你"这个团队认为什么会出错". 而**写下来了却每天被违反** 的那些, 就是最该升到判据级的红线  它们不需要你去猜问题在哪, 违反次数就是现成的证据

```bash
# 1. 找出所有写着规则的文件
git ls-files | grep -iE '(^|/)(AGENTS|CLAUDE|CONTRIBUTING|README)\.md$|规范|RULES|STYLE'

# 2. 逐条把规则变成一次 grep。用规则里的关键词, 数命中
grep -rn 'fetch(' web/src/views | wc -l          # "API 统一走 src/api/ 层" 被违反了多少次
grep -rnE '^\s*(import|from)\s' backend/app/api | grep -c 'repo|mongo'   # "router 不得直连数据库"

# 3. 命中分布: 光有总数不够, 要看散在哪些文件
grep -rln 'fetch(' web/src --include='*.vue' | sort
```

三条判读规则

- **命中 0 处** → 当前扫描未见违规, 不代表以后不会违反; 用户/宿主已要求的标准仍要有判据或明确的覆盖证据
- **命中少数几处** → 对照错误代价、用户标准和控制成本评估, 不只按数量否定建设
- **命中成片** → 优先处理, 目标标准保持明确; 存量按逐文件基线过渡, 不把欠账直接升格为永久阈值

**注意这条规则本身有没有被误读**. 规则说"不在组件中直接调用后端接口", 而某处 `fetch` 其实在`utils/` 里、或在测试夹具里  数之前先确认命中的是不是规则真要管的东西

## 三、信号 → 假设

|信号|可能的根因|值得试的红线|
|-|-|-|
|同一类 review 评论反复出现|约定只存在于人脑里|该约定的确定性检查(最便宜的起点)|
|**规范文档写了 X, 而 X 被违反 N 次**|规则停在文字级, 从不执行|X 的判据 + 现状棘轮(见第二节)|
|`fix lint` / `fix ci` 提交成串|门禁跑得晚或没人本地跑|把该检查前移到提交前的那一层|
|少数文件 churn 极高且体量大|职责没切开|行数上限 + 该文件的拆分|
|大量 `# noqa` / `@ts-ignore` / `eslint-disable`|规则被逐条绕过|棘轮: 冻结现有豁免数, 只拦新增|
|`git log` 里出现事故式回滚|某条路径缺少兜底|事故规则 + 一条能拦住它的判据|
|路由/接口在两个地方各写一份|契约无单一真源|契约快照(生成 + diff)|
|测试改了却验证不出行为变化|测试是摆设或测细节|先修测试, 别急着加覆盖率门禁|
|CI 超过 15 分钟|门禁全堆在 CI|按路径分流 + 挪走慢检查|

## 四、必须亲自读的东西

扫描给的是候选, 结论要靠读

- 已有的 agent 上下文与规范文件, 且对账它们与代码是否一致(第二节就是在做这件事)
- 入口文档的**分布**: 哪些目录有 `AGENTS.md` / `CLAUDE.md`、哪些该有而没有. 只看根目录有一份就收工, 正是本项最常见的漏检形态; 判据与清单命令见 templates/context-layers.md
- 2–3 个代表性模块, 每端各一个(后端入口 + 服务层, 前端页面 + 数据获取), 看真实的分层与命名习惯
- churn 最高的前几个文件
- 现有门禁脚本的**头部注释**  通常写着它拦什么、豁免语义、以及它为什么存在

## 五、历史不够用时怎么办

两种情况, 处理不同

**完全没有 git 历史**(新仓、刚初始化). 只能请用户口述最痛的 2–3 个具体例子(哪次、什么后果、怎么修的), 并把没有证据的红线一律标"预防性"

**有历史, 但历史里没有门禁型失败信号**(例如 285 个提交全是 `feat` / `fix` + 中文描述, `revert` / `fix lint` / `fix ci` 一条都搜不到). 这**等价于拿不到失败史**  别把它当成"没问题". 真正的入口是另外两条

- 第二节的"规范文档 vs 实际违反次数"  它不依赖提交信息
- 用户口述

从最低成本、最低误报的几条开始(格式化、类型检查、import 方向), 先把"证明有效"的回路建起来, 再谈结构性的约束

## 六、输出格式

每个发现三行, 不要写成散文

```
现象: backend/app/services/foo.py 1,240 行, 近半年改动 47 次(全仓第一)
推断: 职责过载, 每次改动都可能碰到无关逻辑; 没有上限时它只会继续长
置信度: 高 — 文件大小与 churn 都是直接读数, 不依赖推断
```

**单独分流**: 如果 churn 榜前列出现协作文档或规范文件, 先核对它的真实读者和执行机制; 属于 GitHub 协作输入的交给远程文档阶段, 不把文字约定伪装成机器门禁.
