# 全景文档的最小可核查契约

写明项目根、扫描时间、运行环境、代码库边界及证据覆盖范围. 按"本地质量 / GitHub 协作文档 / GitHub 工作流"分区, 每条记录项目专属路径、实际入口、执行状态(已实测/仅配置/建议/未知)、通过与失败机制、最近验证及维护成本. 附一段已做好的部分和一段明确不装及其理由; 若项目没有 GitHub, 远程两栏写不适用及判据, 不伪造 workflow

用 Mermaid flowchart 绘制从"开发者改动"到"提交/推送/PR/合并"的路径, 按本地、远程协作文档、远程自动化区分泳道; 只画实测的实线, 用虚线画配置未验证或待建链路. 在图下提供"节点 → 文件路径/命令/运行证据"对照表. 不要复制下列示意为成品

```mermaid
flowchart LR
  A[改动] --> B[本地检查]
  B --> C[推送]
  C -. 尚未验证 .-> D[远程检查]
```

还要列出候选模板逐项裁决表: 规则编号、覆盖路径、现状证据、采用/调整/不适用的理由、检查点、正反探针和生效状态; Python 文件存在时明确列 PY-01..04 四项, 不可缺项. 记下基线数字的计算方法、候选红线的取舍、负向探针和合规控制组结果、决策记录链接. 仅盘点时不要求真实 FAIL 演示; 只有宣称新门禁已落地时, 才必须附正反实测与接线证据. 把维护/更新条件写进文档, 让下一次调用先校对事实而不是追加时间线
