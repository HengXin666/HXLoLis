# 三层防守: 为什么一层不够

存量欠账用**棘轮**(只拦新增)处理, 而棘轮的全部威慑力压在"阈值和被豁免的那几条有没有被悄悄放松"上. 三条机制各管一段, 缺一条就有明确缺口

|机制|管什么|它管不了的|
|-|-|-|
|**棘轮**|**方向**: 水位只许降|悄悄删一条豁免再补一条新违规(总数不变)|
|**指纹**|**可见性**: 口径一变就 FAIL, 逼你显式承认|方向: 只要同步改了指纹, 它照样满意|
|**探针**|**有效性**: 规则真的会红|覆盖不到的路径(所以分流表自己也要被覆盖校验)|

三者互相补位, 不是三选一

---

## 指纹: 把"门禁有多严"变成可见的

**问题**: 放松一条门禁只需要改一个数字, 而那个数字在 review 里毫不起眼.

**做法**: 抽取"决定严格度"的字段做成指纹快照 阈值常量、白名单条目集、各棘轮基线、linter 配置里的规则开关. 任何一处变了就 FAIL, 要求显式跑一次 `--update`

关键区分: **只抽"决定严格度"的字段, 不抽显示名**. 改 `label` 文案、换个排版都不该动指纹; 而加一条豁免、删一条门禁、给某个检查接上 `|| true` 必须 FAIL. 抽多了会变成天天报警, 所有人去跑 `--update`, 报警器退化成确认键

**指纹要分两组**  它们回答的是两个不同的问题

|组|问题|来源|
|-|-|-|
|一|每条门禁**有多严**|阈值常量、白名单条目集、棘轮基线、linter 的规则开关|
|二|门禁**还跑不跑**|门禁注册表、hook 的注册配置、CI 的 job 定义|

第二组容易被忽略, 但第一组有个说不出口的前提: **它们全都假设门禁确实会被执行**. 从注册表删掉一行, 该门禁在全部检查点上同时消失; 摘掉 hook 注册, agent 每轮结束时不再跑任何门禁  这两种情况下第一组的指纹一个字都没变, 照样 PASS. 探针也拦不住(它直接调门禁脚本, 不经过总线, 证明的是"门禁会红", 不是"门禁被接上了")

---

## 探针: 证明门禁真的会红

**问题**: "我加了检查规则"和"检查规则真的会拦下违规"是两件事. 规则被改坏、锚点被删掉、
路径算错, 都会让门禁静默失效而没人发现

**做法**: 对每条规则构造一份**故意违规**的最小输入, 断言它 FAIL 且退出码符合预期.

**控制组同等重要**. 只有违规组时, 一个"对任何输入都报红"的坏门禁会显得完美. 所以每条规则至少配一条 PASS 控制组, 而"只改文案 / 只重排格式"这类**不该报警**的改动也要被显式钉成控制组  否则指纹会天天 FAIL, 所有人去跑 `--update`, 报警器就退化成确认键

**安全**: 夹具一律建在系统临时目录里, 跑完即删, **绝不写真实仓库**. 扫描根、白名单、
决策记录根都通过环境变量指向临时目录  所以"门禁的扫描根必须可被覆盖"是写门禁时的硬约束, 见 gate-bus.md 的「硬约束: 扫描根必须可被覆盖」

**代价与位置**: 探针要起几十个子进程, 所以它**不进 Stop hook**, 承担者是 CI 的专门 job
与手动命令. 改门禁本身时必须手动跑一次

**接线也有探针**: 除了"规则会红", 还要证明"删掉注册/接上 `|| true` 会被拦下".
这是唯一能覆盖第二组指纹的机制

---

## 白名单不是免检名单

豁免机制是必需的(否则装不上), 但它有两条铁律

- **双向校验**: 条目一次都没拦下违规(目标已拆分 / 改名 / 已删)= **陈旧条目 → FAIL**, 删掉它. 只查单向(白名单里的文件存不存在)的机制会积累一堆没人敢删的死条目
- **粒度尽可能细**: 能写到单个函数、对某一个模块的豁免, 就不写整文件. 豁免一条违规是还债, 豁免一个文件是又签一张空白支票
- **行数豁免必须带登记上限** `路径|N`: 挂上豁免之后文件长过 N 依然 FAIL

同理适用于任何"显式登记的清单"(孤儿决策记录基线、依赖白名单、允许的例外): **只减不增**要靠机制保证, 靠自觉的清单一定会长

---

## 静默失效的清单

红线集真正的敌人是"什么也不发生". 上线前逐条自查这些形态

- hook 脚本路径写错 → 退出码落在"非阻塞"分支 → 与"没发现问题"完全一样
- 门禁从注册表里被删掉 → 所有检查点同时不再跑它
- 依赖产物的门禁读到了上一轮的旧产物 → 判绿
- 分流表漏了一类路径 → 改了东西却一条门禁都不跑
- 白名单里的目标已经不存在 → 豁免永远生效, 且没人发现
- 门禁的判据只扫描了目录 A, 而代码已经搬到目录 B → 全绿

对照做法: hook 有冒烟测试; 注册表进指纹; 产物在本次运行内登记; 分流表有覆盖校验; 白名单双向对账; 扫描根写在门禁头部注释里并被 review

其中前半部分可以由**总线自身**在设计时消掉(未知参数报错、preflight、`produces`/`requires`、未知路径不跳过 见 gate-bus.md), 后半部分只能靠上面的对账机制. 这也是为什么"取证的结论"和"总线的形状"要分开决定: 前者决定装什么, 后者决定它会不会悄悄失效
